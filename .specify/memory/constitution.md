# 回甘 Constitution

## Core Principles

### I. 已确认需求与真实授权

设计和实现必须依据[现行规格 08](../../specs/001-first-release/08-current-spec-and-acceptance.md)，历史分册服从后续确认。业务缺口不得凭模板默认值补成作者决定；局部技术细化按既有授权完成。规划检查必须标明本批范围和未解决前提，不以工具成功代替批准。

### II. 固定源码与资料归属

源码必须从确定的 Git 引用读取，读取失败报告实际原因，不静默换工作区。源码只引用、导出例外和个人资产保护按 08 对应规则执行。备份恢复限于已定文档范围，不借实现增加复杂恢复系统。方案必须明确数据的根目录、写入者与失败后的结果。

### III. 共用规则与最少必要机制

命令和服务必须共用业务规则，按[目录职责](../../docs/development/directories.md)划分 core、application、adapters 与入口。AI 判断教学语义，程序处理机械工作。架构不得复制两套更新／校验逻辑或为未批准功能增设平台；必要复杂度在 plan 中解释。

### IV. 分层验证与独立审查

按[验证约定](../../docs/development/verification.md)检查程序行为、Skill 行为和实际阅读教学效果。实现者自检不算独审，作者体验不代替技术验证。规划必须给出可观察场景、失败边界和必要检查；未运行、失败与未验收状态必须真实保留。

### V. 官方文档结构与持续维护

正式 spec、plan、tasks 必须沿已安装 Spec Kit 的相应技能与原版模板维护，细则见[Spec Kit 接入](../../docs/development/spec-kit.md)。局部更新保留结构和跨文件一致性；需要偏离时在聊天中说明具体原因、影响和替代办法，不能静默换成自创格式。安装完成不等于产品设计已完成。

## 工程边界

技术栈、安装与导出方向引用 [03 U102](../../specs/001-first-release/03-web-delivery.md)，文件落点引用目录规范。产品 Skill、开发技能与目标项目资料分开；Python 只可用于开发辅助，不作为回甘产品必需依赖。官方模板中的多项目结构和性能示例不是项目决定。

## 开发与验证

主脑派单、作者转交新执行会话、执行自测并调用审查子代理、回执交回主脑，按根 [AGENTS](../../AGENTS.md)及[任务流程](../../docs/development/workflow.md)执行。plan 的门禁检查必须核以上原则并引用实际设计依据，发现冲突说明证据与处理状态，不以空占位或笼统“通过”代替。Git 与外发按对应授权办理。

## Governance

本文件将已批准原则提供给 Spec Kit 规划门禁，不另立产品事实或取代作者当前明确指令。主脑按[维护约定](../../docs/development/maintenance.md)维护；改变业务结果仍由作者裁决。每次修订记录原因和影响，更新本文件版本与日期：原则不兼容变更升主版本，新增原则升次版本，非语义修订升补丁版本。审查核本批与原则的一致性，细节主定义继续通过链接复用。官方模板、技能和共享脚本不因填写本文件而改写。
