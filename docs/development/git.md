# Git 与交付

只由本次明确的唯一 Git 写负责人操作；主脑与执行分时交接，审查只读。

## 开工与保护

- 日常在原项目目录串行交接，不自动建立 worktree。首次写入核 `git status --short --branch`、本地分支、dev 近期提交及第一父链、现有 author／committer 身份；有远程时核已知远程状态与信息时效，不凭分支名或时间猜最新。
- `dev` 为日常交接基线；从最新已认可 dev 开 `codex/<类型>-<主题>`，继续同一工作可复用分支，不直接在 dev 实现。作者指定优先。
- 署名沿现有 `pioneer <zhao.ming.chun@qq.com>`，不添加代理署名。身份不符先报告，不擅改全局或仓库 Git 配置。
- 切分支或合并前核未提交内容及可能被覆盖的忽略文件，保护依赖、构建、实验数据和待验资源。未知来源改动只停相关操作，已知无关改动隔离保留；不代交、强清理或覆盖。
- 必须隔离时先说明原因、基线、路径、资源保留与清理条件，经作者明确同意才建 worktree。待验服务依赖当前目录时，先按[资源规则](verification.md#resources)固定必要输入或停止服务，不能让切分支悄悄改变候选。

## 提交与候选

- 在提交授权范围内，按有意义成果精确暂存，提交前核暂存差异、必要检查和文件归属，排除凭据、临时产物与无关改动。说明用 `docs:`、`feat:`、`fix:`、`refactor:`、`test:` 或 `experiment:` 加中文目的。
- 候选绑定批准依据、比较基线和提交 SHA；修复另提交，不 amend、rebase 或重写已绑定的历史。派审、冻结与写入交还见[任务流程](workflow.md#review-handoff)。
- 派单或直接维护指令明确“保留候选”或“满足门槛后合 dev”；未指定时保留候选。作者要求先验收时，即使技术检查通过也等待，不把实现或规范维护自行扩成合并。

## 整合与收束

1. 获准合 dev 后，核 dev 是否前进。有新提交先查交互；需更新候选时用普通合并，补受影响检查并重判独审和作者验收是否仍适用。涉及业务取舍或来源不明的冲突，暂停该合并并交回，不自行择边。
2. 确认获批范围完整、必要检查及独审满足、无未处理阻断，并完成[适用作者验收](verification.md#author-acceptance)，再以正常 `git merge --no-ff <功能分支>` 合 dev。作者明确批准的阶段接受按其范围记录，不冒称缺陷已修或体验已通过。
3. 核合并父提交、候选包含关系、实际差异、工作区及本地文件保护状态，确认 master／main 未被改动。合并改变成果时补受影响检查；仅文档归档可核差异后复用证据。
4. **收到「合并到 dev」即由本次 Git 负责人完成本地收尾。** 切回 `dev`，先以 `git merge-base --is-ancestor <任务分支> dev` 确认分支尖端已进入 dev，再核 `git worktree list` 和试读服务实际使用的构建、项目路径。满足条件就执行 `git branch -d <任务分支>`，用 `git branch --list <任务分支>` 和 `git status --short --branch` 核实结果并写入回执。正常收尾仅处理本次任务分支。
   - 合并前的「保留候选待验」随合并授权结束。用候选 SHA、合并提交、独审和固定构建追溯；待作者体验时继续保留试读所需的构建与资料。
   - 作者明确要求**合并后仍保留该分支名**、分支有独有提交、仍由其他工作树检出或服务确实依赖该分支时，保留并写明具体依据及解除条件。`-d` 拒绝时查明原因，不强删。作者另行要求整理旧分支时逐支核对，远程分支需单独授权。
5. 经批准建立的 worktree，确认成果已整合、未提交与忽略资源已保护、服务已脱离后才正常移除；占用或归属不明则交回残留与解除条件。

合并说明至少包含目标、范围／来源分支／候选、实际验证与证据、独审版本及原文入口或免审依据、作者验收范围、限制与遗留。回执维护实际当前状态，最终聊天给可读提交和整合结果；不为补回执自身 SHA 或尚不存在的合并 SHA 循环提交。

master／main 的移动、合并或回退须作者本次明确授权；推送、发布、版本升级亦须对应授权。不强推、不用底层引用构造合并。实现、检查、独审、作者验收、dev 整合、推送和发布分别报告；合入 dev 不等于已更新安装包或运行服务。
