# 开发规范的持续维护

作者于 2026-11-16 明确：开发规范属于主脑职责，首版无需完美，随项目逐步增加适配，未来可以扩展技能与规则。原话见 [D001](../work/2026/11/D001-development-standards/task.md)。

- 主脑可直接修改规范、角色入口、模板、技能路由和项目适配；常规维护无需把技术规则逐条重新交作者设计。
- 修改依据优先采用实际任务摩擦、失败证据、重复问题及项目已经确认的取舍。可提前规定高影响边界，不为假想情况堆流程。
- 发现已确认的问题，先定位影响并判断当前修正的成本，在获批范围内完成必要处理；不能仅以“以后再说”“保持历史”或避免改引用为由维持已知问题。确需保留现状或延后时，说明具体用途／风险、当前处理与延后的代价、影响范围、负责人及再次处理的条件；涉及作者使用后果时按决策边界取得对应决定。此原则不扩大权限，也不取消两轮修复停点。
- 找到现有主定义后修改一次，其余引用；现行正文保持当前规则，历史通过 Git 和任务原文追溯。已批准任务原文、审查原文和唯一证据保留。
- 获准迁移任务资料时移动唯一原件、同步索引与引用并检查完整性，完成后移除原位置，不默认留副本或跳转目录。批准内容、审查结论及当时版本保持不变；相对链接等定位可作机械修正，在维护回执记录迁移依据、新旧位置及原版本。历史正文中的当时命令／路径保留为证据，不再作为现行调用入口。
- 通用教程能由技能或工具承担就引用；新增规则写清触发、责任和完成条件。规则无效时调整或删除，不能只不断追加。
- 小维护以提交说明和必要验证留证；跨会话派单留工作单，影响职责、权限或交付门槛的调整保留完整批准依据并独审。作者明确要求本会话直接维护、不另建任务时，在已有规范维护回执追加本轮日期、关键原话、范围、基线与收尾要求，独审原文追加到对应 review；不新编 D 编号、不改旧批准任务，也不借此省略验证或独审。
- 未来技能可按真实需求扩展。主脑先核用途、来源版本、许可、完整配套、宿主与运行条件，说明和已有技能的分工；再完成项目内接入与检查。
- 技能带来的全局安装、外发资料、费用、破坏性操作、改变产品运行依赖或作者使用方式，不包含在一般规范维护授权内，须先说明并取得对应决定。
- 开发规范不能替代产品裁决：改变回退、源码保存、导出、笔记等已确认行为，必须回到规格与作者决定。
- 验证适配有效性看接单、实现、审查与交回是否顺畅；不把规范篇幅、技能数量或模板填满程度当质量指标。
