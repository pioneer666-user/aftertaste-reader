# 任务与交接

供派单、接单和交回时读取。三个角色按根入口协作；主脑直接维护规范是作者已批准的职责。

## 一项完整目标

- 任务类型选主要交付：探索、设计、实现或规范。必要验证属于同项；探索结论、设计认可不自动授权产品实现。换主要类型或明显扩大目标，由主脑另派短任务并引用前一成果和有效批准；同类小范围调整沿下节记录。作者明确要求直接维护、不另开任务时，沿[维护约定](maintenance.md)留证，不为流程补造编号。
- 新任务用 `docs/work/D编号-主题/`，编号按已有目录递增。派单用 [task 模板](../work/_templates/task.md)，回执用 [handoff 模板](../work/_templates/handoff.md)。索引只导航，不复制状态。
- 目标、范围、产品依据、基线、验收与负责人明确后即可开工；不为填模板补造需求或未使用文件。
- 材料列表只列本批必需规格与特殊入口；额外规则按“动作 → 文件／章节”注明。根 AGENTS 已列的通用规范不再一律列为接单必读，已给出且仍有效的落点和证据直接复用；实际执行写入、验证、Git 等动作前仍须核对应规则。
- 派单按[目录职责](directories.md)写明本批源码／指南／测试落点；实验材料用与任务相同的 D 编号放 experiments，运行输出另定隔离位置。不得把正式代码放进派单目录。
- 实施任务引用 `specs/` 中已确认的要求；需完整设计时维护同主题 plan、数据／接口约定和 tasks。小维护在任务中说明方法即可。
- 正式文档编写和更新必须按 [Spec Kit](spec-kit.md) 对应技能与模板；任务说明使用完整流程还是已有材料的增量维护。官方任务清单与协作派单职责不同，验收预期只定义一次。

## 批准、调整与事实

- 批准依据保留关键原话、日期、来源和范围。派单绑定任务路径＋提交；任务原文批准后冻结，分支名不能代替版本。
- 范围或验收调整写同目录 `amendments.md`：原批准版本、调整原话／来源、替代条款、影响及生效候选。只在实际调整时创建。
- 已有授权内的局部技术细化记录在 handoff，无须重新批准；新增业务取舍仍由作者裁决。
- 回执顶部维护唯一当前结论：实际完成范围、候选／基线、自检与独审、作者已验和待验范围、Git 与下一步。收到验收、完成合并或结论改变时就地更新，不另加一份“当前收尾”。普通旧状态由 Git 追溯；需保留的批准原话、失败及累计修复记录标明当时日期与版本，不覆盖成成功叙述。
- 独审原文按 [review 模板](../work/_templates/review.md)在实际审查后保存一次，复核追加；回执只引用报告和处理结果。不能把汇总的“通过”扩写成未发生的逐项验证，也不为记录自身 SHA 循环提交。
- 同一事实只维护一处：spec 管产品要求，plan 管方案，tasks 管实施状态，checklist 管需求表达质量，handoff 管本次结果。交回核受影响主定义与真实成果一致；索引只导航，backlog 只维护小事项及成果入口，不逐级复制任务状态。
- 跨会话只能传入口时，文件必须含足够的任务与依据；外部路径读取不了，派单方补充必需原文，不要求作者搬运日志。
- 早期 AR1 原话继续保留外层仓库位置，见产品 README；新任务不得继续依赖外层目录。独立克隆／发布前的旧依据交接仍需明确处理。

## 独审与收束

- 产品实现、产品 Skill 行为变化、数据写入、接口／版本协议变化默认需要独审，由执行调用审查子代理。
- 主脑直接维护规范也可调用独立审查子代理；影响职责、权限或交付门槛时需要独审，检查入口、授权、角色、技能和验证是否闭合。纯文档按文档影响查，不套产品全套测试。
- 拼写、链接等小维护可由主脑明确免审并说明理由；执行不能自行取消任务要求的审查。免审仍完成必要自检。
- 审查候选用提交固定；修复另提交，审查结论标明覆盖版本。只整理回执的后续提交可复用成果审查，明确其无行为变更。
- 结束条件：获批目标完整、自检完成、所需独审问题已处理、限制如实交回；需要作者体验的候选保留待验。未达条件交回停点，不能冒称完成。
- 作者收到一份 handoff 入口即可；主脑接回不替代作者验收，也不自动授权下一单或发布。

## 派审与写入交还

1. 派审方提供职务、批准任务／直接指令与有效调整、比较基线、固定候选、实际差异、相关规格、可复用证据和未验证项；不只提供完成摘要。只读审查不切分支、不代修、不提交。
2. 送审后保持本次被审文件、构建及输入不变，直到审查明确交还写入。需改动时先结束本轮采集，保存已取得证据及缺口，再形成新候选；不能边修边让审查读取漂移的工作区。
3. 审查结束核候选与输入仍一致，收束自己启动的浏览器／服务／采集资源，返回原文并明确“采集结束，可以恢复写入”或尚未交还的原因。未启动运行资源的文档审查注明不适用；发现版本漂移时说明受影响结论与复核安排，不用关闭浏览器代替版本核对。
4. 派审方取得写入交还后保存原文、修复另提交并复核受影响项。交还只代表可恢复写入，不代表审查通过或允许合并。资源归属沿[验证规则](verification.md#resources)。

<a id="mainbrain-handoff"></a>
## 更换主脑会话

- 作者要求换主脑时，交出方在现有相关 handoff 留带日期的短交接：当前目标及批准范围、实际开发／运行版本、最新回执与必要材料入口、未决事项及再处理条件、下一步建议。注明核验时间和未实查项，引用主定义，不复制历史或把建议写成批准。
- 接续方读根入口、本职角色和该交接，再核实际 Git；按下一动作补读相关材料。历史记录与现场不一致时先核差异，复用有效独审和批准，不要求作者重讲已确认决定。换会话不扩大提交、合并、发布或数据操作授权。
