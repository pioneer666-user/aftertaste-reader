# 开发协作反馈观察

主脑在接回任务、准备下一单时维护。这里保存实际使用反馈与观察依据；现行规则仍以 `docs/development/` 为准，记录建议不等于批准改流程。

## 观察方式

2026-11-17（Asia/Shanghai），作者在本会话转交 D007 反馈后明确：“一个问题第一次被反应先忍住（除非这个问题很严重），第二次也忍住，第三次再抽象”。本页按这一指令记录：

- 一般流程摩擦第一次、第二次先记录具体场景和代价，沿现行规则完成任务；第三次独立出现时，再判断是否存在共同原因、是否值得统一适配。三次是考虑抽象的时机，不是必须增加规则的指标。
- 同一任务中的多处表现、多个技能重复同一句说明、同一反馈被转述多次，都不自动累计为多次。关联但不同的问题分别记录，不为凑次数混算。
- 正确性、数据安全、权限边界或阻断交付等严重问题及时处理，不等待第三次；一般反馈的观察期不能用来延后已经确认应修的产品缺陷。处理仍沿[维护约定](../development/maintenance.md)与当前任务授权。
- 主脑负责接续；再次发生时补任务、日期、实际后果和处理办法。确定要改时再进入维护或[待办](backlog.md)，在此链接结果，不复制另一套完成状态。
