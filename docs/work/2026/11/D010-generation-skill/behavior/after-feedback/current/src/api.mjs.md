## 接口入口依赖创建服务

对照 `src/api.mjs` 第 1–2 行。入口通过导入使用创建服务，业务步骤在服务中组织，入口接着把结果变成调用方能消费的响应形状。前两篇已经讲过服务如何使用数量规则，以及如何更新订单集合。

从调用关系看，这样的职责划分有利于让批量导入、命令行等其他入口复用同一创建流程，代价是读一次请求需要跨文件对照。这里的复用情景是条件性的取舍分析。

## 成功路径先完成业务，再组装响应

对照 `src/api.mjs` 第 3–5 行。导出的入口函数接收请求体和订单集合，把两者传给创建服务。服务调用成功后，入口返回一个普通对象，携带状态码 201，响应体使用服务返回的订单。外层调用方可以继续利用这个对象组织响应。

服务调用发生在成功返回之前。因此数量检查、对象建立、集合追加和审计辅助调用，都要沿服务中的顺序走完，入口才会得到创建结果。响应体与集合中的新增订单共享同一个对象引用。完整例子放在本文最后一个块中，把这些步骤接到同一组输入上。

## 异常路径统一形成失败响应

对照 `src/api.mjs` 第 6–9 行。受捕获区域中的异常会转入这里，入口返回状态码 400 和固定错误体。数量规则抛出的校验异常会进入这条路径，服务调用期间发生的其他运行异常也会被这一捕获范围接住。

统一响应让调用方拿到稳定的失败形状，相应代价是不同异常原因在返回结果里被合并。理解调用失败时，需要继续对照服务在哪一步退出，以及集合已经发生了什么变化。

异常捕获决定返回对象的内容，集合状态仍由服务的执行顺序决定。若未来某个追加之后的辅助动作改成会抛错的外部操作，可能出现失败响应与已追加记录同时存在的结果。这是依据顺序作出的条件推演。当前审计辅助函数产生的文本会被调用处忽略。

## 用同一合成情景走完输入到结果

下面用活动报名作独立教学情景。数值与初始集合是合成输入，过程依据固定提交推演。请求体使用当前数量字段约定，订单集合承载报名记录。

### 人数有效时

| 阶段 | 输入、处理与结果 |
| --- | --- |
| 初始输入 | 集合里已有编号 1、2 的两项记录。请求体的数量字段为文本“4”。 |
| 规则处理 | 文本转换成数字 4，通过整数与范围检查。 |
| 服务状态变化 | 建立编号 3、数量 4 的记录，并加入原集合。集合长度从 2 变为 3。 |
| 辅助动作 | 审计辅助函数产生文本，返回值被服务调用处忽略。 |
| 最终结果 | 服务返回刚加入的记录。入口返回状态码 201，响应体为编号 3、数量 4 的记录。集合中也保留这条记录。 |

### 人数无效时

这一遍重新从两项初始集合开始，把请求体的数量字段改为文本“2.5”。

| 阶段 | 输入、处理与结果 |
| --- | --- |
| 规则处理 | 文本转换成数字 2.5，整数检查失败并抛出异常。 |
| 服务退出 | 异常向上传递，流程在建立新订单和追加集合之前退出。 |
| 接口捕获 | 入口进入异常路径，形成状态码 400 和带固定无效订单说明的错误体。 |
| 最终状态 | 调用方得到失败响应，原集合仍是编号 1、2 的两项记录。 |

两遍过程共同展示了职责衔接。规则决定数量是否可用，服务决定业务步骤与集合变化，接口入口决定调用方最终拿到的响应形状。可结合前两篇服务讲解的 `m3vuiqzi`、`cj9208pf` 块继续对照。
