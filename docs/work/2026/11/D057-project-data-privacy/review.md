### 新发现

**暂存目录的权限可能比读者为资料目录设置的权限宽。** 例如，仓库的 `.git` 允许另一位本机账号读取，但 `docs/aftertaste` 的默认 ACL 只给读者权限。原实现把带正文的文件创建于资料目录下，继承该处权限。新候选在 `.git` 下创建暂存目录和文件，`open('wx')`、闭环的 `mkdir/open` 都使用暂存位置的默认权限，然后以同卷硬链接或重命名发布。较宽的暂存权限会让正文在发布前就可能可读。NTFS 硬链接沿用文件安全描述符，POSIX 硬链接与重命名沿用文件身份，因此发布后也可能带着暂存目录赋予的权限。这一结论基于候选代码和平台行为，未用第二账号执行写入式复现。[暂存目录](../../../../../src/adapters/git-staging.ts#L6) · [文档发布](../../../../../src/adapters/document-store.ts#L44) · [闭环发布](../../../../../src/adapters/loop-store.ts#L74) · [Windows 硬链接](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw) · [Linux 默认 ACL](https://man7.org/linux/man-pages/man5/acl.5.html)

修复需同时确保暂存正文受保护、发布后仍遵守资料原位置的访问范围。两种收敛方式的判断如下。

- **保留同目录暂存。** 采用工具能在落盘前确定的临时路径，随批次预查其实际 Git 状态，再按读者授权写入。这可以沿用资料目录的权限继承。路径在本批仍可见时，提示范围应包含相应临时资料。
- **先在资料目录创建空条目，再移动至 Git 元数据内写正文。** 空条目也会出现在工作树，可能因中断而遗留或进入暂存，所在目录还可能透露项目结构。这里也适用本批路径预查和授权要求。即使保留了空条目原有的 ACL，移动也会失去原父目录对路径访问的限制，例如从 `0700` 的目录移出继承普通 `0644` 的文件。该方式还需验证 Git 元数据内暂存位置的访问保护。建议用暂存目录与资料目录权限不同的 NTFS／POSIX 样例，分别核写入时和发布后的权限，并保留原有失败清理及锁行为。
