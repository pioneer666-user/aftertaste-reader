# D012 · 文件依赖图的阅读与布局保存

## 目标与批准依据

用户在本地阅读器里看懂文件之间的直接依赖，按自己的思路摆放节点、分组，再次打开同一项目时接着上次的布局读。任务类型为实现。主要工程量放在布局计算、项目文件读写与恢复。页面沿用 D011 的双语界面，提供能读、能操作、能辨别保存结果的入口。

2026-11-18（Asia/Shanghai），作者在本主脑会话确认“我选择你说的第一种，就是你推荐的做法”，即单击节点先选中，留在图上，另点“阅读讲解”才打开文档。作者要求“重点放在逻辑处理上，页面可以不那么细节，后面单独针对ui和ux做一单”，并指定执行独审、交回后主脑再派另一名子代理独审。本单按这两道独立审查交付。

### 交付与验收

| 编号 | 在实际使用中应看到的结果 |
| --- | --- |
| G01 读关系与进入讲解 | 从本地阅读器打开当前项目的依赖图。箭头从被依赖文件指向使用者，边可读到原有原因；允许环及自环。单击文件留在图上，能辨认所选文件、直接关系及依赖核对状态。讲解入口依据磁盘上实际存在的文档，有讲解才可打开 D011 对照页，无讲解给出状态。拖动节点不会误开文档，读完返回原画布视野。未核对、无讲解、已核对且无依赖分别表达，缺图、空图与读取失败有可辨状态。 |
| G02 自由布局与分组 | 可拖节点、平移缩放、创建和命名多个组、显式加入与移出成员、拖整组。拖组时只有该组成员按相同位移移动，相对位置保持；组框随成员实际位置和尺寸确定。放在框内的非成员仍然独立，移走最后一个成员后空组消失。主动重排沿 D004 的简单方案保留组名和成员。分组、拖动和重排均不改变图上的文件、边或依赖原因。 |
| G03 保存与恢复 | 按用户完成的操作自动保存位置、组名、成员及平移缩放。只在对应布局已成功落盘后显示已保存。连续操作即使先后返回次序不同，也以最新有效布局为准。看到已保存后关页面、停服务，再用新的浏览器上下文启动同一项目，比对文件、节点、组与视野。另一项目即使有相同文件名，也有自己的布局。 |
| G04 图内容变化 | 文件路径身份沿 D009。同一文件的依赖原因、连线或核对状态变化，保留它的位置和组；新增节点排在已有排布外侧；确认移除节点后，其余节点原地不动，相应成员引用清除，空组消失。图暂时不全、损坏或读不到时保留最后有效布局；不得据临时缺失清除用户数据。把判定有效输入及协调增删的依据写入协议，并以真实图工具更新验证。 |
| G05 写入失败与竞争 | 写入仅限当前图的专用布局文件，服务沿用本机及指定项目的边界。写入失败时留住最后一份有效文件和本页尚未保存的操作，给出可行的重试途径。旧标签页迟到的保存不能覆盖另一个标签页已确认的新布局；冲突须可见。布局损坏时报告具体问题，打开页面不会用默认值覆盖原件。讲解、源码、依赖图及其他用户资料在布局保存前后保持原样。 |

本批的正式需求、布局数据模型、读取与写入契约、实施清单归 `specs/007-dependency-canvas/`。这是新能力，按 [Spec Kit 阶段入口](../../../../development/spec-kit.md#stage-entry) 使用 specify、plan、tasks、analyze、implement 及对应官方模板；已定产品结论与 D004 证据直接引用。把 G01—G05 映射到任务与检查即可。正式实现沿 `src/core/`、`src/application/`、`src/adapters/`、`src/server/`、`src/web/` 的实际调用链，测试在 `tests/`，用法补入 [本地阅读说明](../../../../usage/file-reader.md)。按实际能力更新 08 对应状态。

实施用 Ponytail full。布局规则适合用 property-based-testing 的独立预期，例如同一位移与存续位置保持。界面沿[正式页面适配](../../../../development/skills.md#impeccable)复用现有风格，交付图关系、选中、无讲解、保存中／成功／失败等必要状态，以及双语文案、可读标签和键盘可达的主要控件。作者已确认的点击行为直接实施。

## 验证与停点

1. 用 [D010 合成样例](../D010-generation-skill/sample/README.md)重建 D012 专用项目。沿两条真实依赖线选中 `src/service.mjs`、打开已有讲解后返回，再选没有讲解的 `support/audit.mjs`。区分图的核对状态与讲解有无。运行输出放 `.local/D012/<run-id>/`，使用单独端口；保留 [D011 待验入口与样例](../D011-file-reader/handoff.md)。
2. 用明确的坐标和成员清单验证核心规则。重点包括组框内夹有非成员、两个不同组、缩放后拖组、重排保组，以及先摆好再增删节点。真实服务加浏览器至少走通一次“摆放 → 看到已保存 → 关页面和服务 → 新会话重开 → 对照磁盘与可见画布”。记录节点画布坐标、成员和视野，检查舍入误差；截图用于辨认操作结果。
3. 通过正式写入路径验证失败、重试及过期保存，核上次成功的文件和当前页面状态；比较布局写入前后图与讲解的内容。测试串行，按影响进行类型、构建、核心、接口与浏览器检查。回执把实际结果绑定候选，说明证据位置和可重建方法。
4. **执行侧独审。** 执行自测后固定候选，派未参与实现的审查子代理按 Ponytail Review 检查 G01—G05 完整调用链，特别核成员身份、坐标转换、增删及写入保护。按[派审与写入交还](../../../../development/workflow.md#review-handoff)保存原文到本单 `review.md`；发现问题、修复及复核分别绑定提交。
5. **主脑接回后的第二次独审。** 作者转回 handoff 后，由主脑另派一名未参与实现及第一次独审的子代理。以交回的最终行为候选为准，独立从布局代码和实际入口构造输入，优先查第一次未覆盖的组合，例如拖组后改图再重开、连续保存遇到迟到写入。给它基线、差异、可复现输入和已有证据，要求写明自己验证了哪些不变量、遇到什么反例；单纯转述首审结论不能完成此项。两次原文在同一 `review.md` 分节归档。发现需修问题交执行另提交，最终候选按受影响项复核；同一问题的两轮修复停点跨两审累计。

若实现路线无法保护已保存的用户排布，说明可复现的场景、受影响的结果与可替代方案，再处理相应部分。涉及改变产品操作、覆盖已有资料或引入额外用户负担的取舍交主脑与作者讨论。
