## 真实使用场景与确认边界（U39）

| 内容 | 作者的真实用途 | 确认边界 |
| --- | --- | --- |
| 全局笔记 | 读代码发现问题，暂时不方便改，怕忘记；先记录，之后集中查看再处理代码 | 需求明确；全局范围、来源关联与处理状态尚需具体设计 |
| 理解标记 | 还没读完整闭环，暂时不理解某块为什么存在；标记不理解，之后涉及该闭环时针对性解释 | 沿用已确认三种状态；闭环如何读取和解释这些标记在模式设计时展开 |
| 块注释 | 记录巧妙之处或值得回看的原因，像读书折角；讲解可能已有相同知识，个人记录主要表达收藏意图 | 真实场景明确；合并为带备注书签是作者倾向，尚待最终确认 |
| 常用文档书签 | 快速回到表单等重要逻辑的讲解 | 作者明确是设想，不冒充已经实际遇到的需求 |

- **FR-055**：提供全局笔记能力，支持用户先记下阅读时发现的代码问题，之后集中查看，便于有时间时再处理；记笔记本身不触发代码修改。这里的“全局”尚未决定是项目内统一入口还是跨项目集合，也不预设必须关联某个文档块。（U39）

本轮 AI 推荐，尚未确认：将块注释和书签合并为“书签＋可选个人备注”，用户可以只收藏，也可以写明值得回看的原因；不再分别建立两套功能。块书签以文档路径＋块 ID 定位；整篇文档书签可作为无块 ID 的文档定位，是否纳入首版继续确认。这不决定任意文本选择提问的定位粒度。

不再沿用上轮“独立阅读待办”作为首版推荐清单：作者给出的直接需要是记录以后处理的代码问题，可先在全局笔记中设计是否需要处理状态，不另外假定开发任务系统。更新说明里的 AI 工作清单仍是另一对象，不与个人笔记自动混用。

建议理解状态、书签及全局笔记允许并存；已理解也能收藏，收藏不表示理解，记录或处理代码问题不自动改变理解状态。个人记录不能从源码重建；保存、与原位置关联及更新后如何保留要随功能讨论，不能因进入新方向而宣称这些问题已经解决。

## 下一步：先设计全局笔记（本轮建议）

先围绕“发现问题，快速记下，之后能找到并处理”设计最小流程。建议首版先做项目内统一笔记列表，笔记正文可独立存在、来源可选；从阅读位置创建时由程序带上来源，允许从全局入口直接写。此处均为推荐，尚未选择实际文件、存储机制、处理状态或自动修改功能。

作者提出的选中片段快速加入笔记、快捷键、颜色分类，记录为后续交互候选；未批准全部进入首版，也不因提前记录就新增正式暂缓事项。设计这些交互时先减少记录步骤，具体按键、颜色含义与分类方式逐项讨论，不让用户为了记一句话必须先配置分类。

## 全局笔记保存讨论（U40）

- **FR-056**：全局笔记支持新增、查看、修改、删除。作者提出保存到指定目录的 JSON 文件，当前作为候选讨论，未锁定运行方式、目录或文件格式。原话见[作者 U40](../../../tasks/AR1-回甘首版需求设计/amendments.md)。
- AI 推荐：首版若按项目保存，使用一个 JSON 文件即可，正文可以是普通文本或 Markdown 字符串；暂不需要数据库。候选路径为 `docs/aftertaste/reader/notes.json`，与可更新的 current 和可清理的 history 分开。路径、单文件组织及正文格式均未确认。
- 最小字段建议为稳定笔记 ID、正文、创建时间、修改时间；来源可选，包含文档路径、块 ID 和记录时的源码提交。无需用户手填这些机械字段；正文修改不更换 ID。未决定引入标题、分类或颜色。
- 建议来源失效时保留笔记正文并提示原位置不可用，不随文档删除或历史清理删除用户笔记。沿用个人记录不可从源码重建的保留原则，具体定位恢复方式未定。
- 保存可靠性建议：真正写入成功才显示已保存；失败保留正在编辑的文字。文件写入采用先写临时文件、成功后替换的方式，避免直接截断原文件；这不等于已经解决多窗口并发覆盖，具体实现未开始。
- U40 曾建议未处理／已处理状态；U41 作者说明实际通常处理后删除，也可能长期保存，因此不继续将二态工作流作为默认推荐，见下节。

普通导出 HTML 不能仅凭项目路径静默写回 JSON。可提供下载导出和手动导入，但下载不保证更新项目原文件；浏览器存储也不是项目目录中的 JSON。支持文件系统访问 API 的浏览器可经用户授权写文件，但有兼容性与权限要求，不能作为不限浏览器的统一前提。本地服务则可实现将页面编辑写入指定 JSON 的接口，仍需开发该接口。

依据：[MDN showDirectoryPicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)、[MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)（2026-11-15 查阅）。以上为能力事实，未进行产品运行验证。若作者要求不限浏览器且点击保存就写入项目，AI 更推荐本地服务；D-001 尚未裁决。

## 笔记留存、标签与保存复杂度（U41）

作者明确：问题处理后通常自行删除笔记，也可能保留长期笔记。沿用已有删除能力，不要求先标完成、不自动删除、不强制归档。作者提出没写完、已写完、有问题、待处理等状态，以及前端、后端、数据等标签作为整理候选；这些名称尚不是已确认枚举。依据：[作者 U41](../../../tasks/AR1-回甘首版需求设计/amendments.md)。

AI 推荐：首版先用可选、可多选的自由文字标签承载整理需要，不另建固定状态流转。原因是写作完成度、是否存在问题和所属技术领域可以同时成立；一条笔记可以同时标前端、待处理，也可以没有标签。标签不自动触发删除、归档或代码修改。标签与固定状态是否分开，等待作者选择；不新增正式暂缓项。

保存澄清：临时文件写完再替换解决的是避免原文件直接被截断、留下半份 JSON；锁或写入队列解决的是多个写入同时进行，两者不是同一措施。不能据此声称防住所有断电或并发覆盖。若最终采用单个本地服务，建议服务内将同一笔记文件的读取、修改、写入依次执行，页面提交单条笔记操作，不用陈旧的整份列表覆盖文件；不因此引入操作系统级全局锁。此建议仅约束经同一服务的写入，不自动解决多个服务或外部编辑器同时修改，也不决定同一笔记的多人协作策略。具体技术实现随运行方式决定，本轮不实现。

## 可行性事实与取舍

静态网页可以用 JavaScript 实现书签、注释和理解标记；交互不是只有服务才能提供。关键区别在于保存位置和数据进入 AI 上下文的方式。

| 环节 | 自包含静态页 | 本机服务或 DSH 适配 |
| --- | --- | --- |
| 点击标记、填写注释、跳转书签 | 可实现 | 可实现 |
| 保存到浏览器 | 可用浏览器存储，但 file URL 行为不能作为跨浏览器可靠持久化保证 | 也可使用，但并非必须 |
| 保存到项目资料中 | 无授权或桥接时需用户导出、复制等明确动作 | 可通过受限接口写文件，仍需实现保存功能 |
| 让 AI 得到记录 | 可以提供复制上下文或导出记录供 AI 读取 | 可以保存成 AI 能读取的项目资料；AI 仍需实际读取，不是存了就自动知道 |
| 分享或换设备 | 浏览器记录不自动跟随原 HTML；需要明确携带记录的方式 | 本地服务也不自动实现跨设备同步 |

依据：[MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)（2026-11-14 查阅）。本地旁证：D:/project/Qiao-Ge-Doc/web/assets/js/annotations.js 已有 localStorage 存取及导出批注的代码；本轮仅只读核查，不把旧阅读器功能自动继承为本项目需求，也未做浏览器运行验证。

## 用来检验功能的讨论场景
