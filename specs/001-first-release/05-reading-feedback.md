## 全局笔记保存讨论（U40）

- **FR-056**：全局笔记支持新增、查看、修改、删除。作者提出保存到指定目录的 JSON 文件，当前作为候选讨论，未锁定运行方式、目录或文件格式。原话见[作者 U40](../../../tasks/AR1-回甘首版需求设计/amendments.md)。
- AI 推荐：首版若按项目保存，使用一个 JSON 文件即可，正文可以是普通文本或 Markdown 字符串；暂不需要数据库。候选路径为 `docs/aftertaste/reader/notes.json`，与可更新的 current 和可清理的 history 分开。路径、单文件组织及正文格式均未确认。
- 最小字段建议为稳定笔记 ID、正文、创建时间、修改时间及已认可标签；U43 以正文内多个链接替代单一来源字段的建议。无需用户手填编号和时间；正文修改不更换 ID。链接是否包含历史版本信息尚未确认，不默认固定历史源码提交。未决定引入标题或笔记颜色字段。
- 建议来源失效时保留笔记正文并提示原位置不可用，不随文档删除或历史清理删除用户笔记。沿用个人记录不可从源码重建的保留原则，具体定位恢复方式未定。
- 保存可靠性：U42 已认可先写临时文件、成功后替换的方式，见 FR-058。真正写入成功才显示已保存、失败保留正在编辑的文字仍为明确提出的配套建议，不扩大本次认可范围。这不等于已经解决多窗口并发覆盖，具体实现未开始。
- U40 曾建议未处理／已处理状态；U41 作者说明实际通常处理后删除，也可能长期保存，因此不继续将二态工作流作为默认推荐，见下节。

普通导出 HTML 不能仅凭项目路径静默写回 JSON。可提供下载导出和手动导入，但下载不保证更新项目原文件；浏览器存储也不是项目目录中的 JSON。支持文件系统访问 API 的浏览器可经用户授权写文件，但有兼容性与权限要求，不能作为不限浏览器的统一前提。本地服务则可实现将页面编辑写入指定 JSON 的接口，仍需开发该接口。

依据：[MDN showDirectoryPicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)、[MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)（2026-11-15 查阅）。以上为能力事实，未进行产品运行验证。若作者要求不限浏览器且点击保存就写入项目，AI 更推荐本地服务；D-001 尚未裁决。

## 笔记留存、标签与保存复杂度（U41）

作者明确：问题处理后通常自行删除笔记，也可能保留长期笔记。沿用已有删除能力，不要求先标完成、不自动删除、不强制归档。作者提出没写完、已写完、有问题、待处理等状态，以及前端、后端、数据等标签作为整理候选；这些名称尚不是已确认枚举。依据：[作者 U41](../../../tasks/AR1-回甘首版需求设计/amendments.md)。

U41 的 AI 推荐已由 U42 认可：首版先用可选、可多选的自由文字标签承载整理需要，不另建固定状态流转。原因是写作完成度、是否存在问题和所属技术领域可以同时成立；一条笔记可以同时标前端、待处理，也可以没有标签。标签不自动触发删除、归档或代码修改。具体要求见 FR-057，不重复设计状态枚举。

保存澄清：临时文件写完再替换解决的是避免原文件直接被截断、留下半份 JSON；锁或写入队列解决的是多个写入同时进行，两者不是同一措施。不能据此声称防住所有断电或并发覆盖。若最终采用单个本地服务，建议服务内将同一笔记文件的读取、修改、写入依次执行，页面提交单条笔记操作，不用陈旧的整份列表覆盖文件；不因此引入操作系统级全局锁。此建议仅约束经同一服务的写入，不自动解决多个服务或外部编辑器同时修改，也不决定同一笔记的多人协作策略。具体技术实现随运行方式决定，本轮不实现。

## U43 · 正文多链接与自动保存

- **FR-059**：笔记允许随时独立创建，不强制先选择来源文档。每条笔记正文可以包含零个、一个或多个文档块链接，可以链接项目内不同文档的块；不以一个来源字段限制笔记关联范围。（U43）
- **FR-060**：用户选中文档块中的讲解后，可通过便捷操作在笔记正文插入内部链接，按文档路径＋块 ID 定位；内部链接需要可与普通网络链接辨认。具体链接格式以及按钮、快捷键、样式或颜色由后续对应设计明确，不自动要求操作系统注册自定义协议，不把选中文字等同于已批准字符级永久定位。（U43）
- **FR-061**：笔记编辑采用自动保存，不要求用户每次手动点击保存；编辑应支持 Ctrl+Z 撤销。自动保存不得因更新编辑器内容而清空当前编辑撤销记录。这里不自动承诺关闭页面后仍可撤销、撤销删除整条笔记或保存完整历史版本。（U43）

U44 认可上轮明确展示的边界：选中文字可以作为链接显示文字，定位目标是所属文档块，不维护精确到字符的永久定位；块消失时保留笔记并提示链接失效。默认跳转 current 中同路径、同 ID 的当前块仍为此前文档中的 AI 建议，尚未由用户明确选择；当前资料与历史资料之间的选择需在链接设计时确认。

自动保存配套建议：短暂合并连续输入后保存，显示保存中／已保存／保存失败，写入失败保留输入；撤销后的正文也进入自动保存流程。具体触发时机和延迟值未定；自动保存不等于每次键入已落盘，也不取代 D-001 对保存通道的选择。

本轮可结束笔记用途与主要功能范围的讨论，进入书签用途；链接编码和编辑交互按作者“到时候”安排在对应设计中补齐，不新建正式暂缓项、不据此开始产品实现。

## U44 · 书签与更新，以及 AI 访问边界

- **FR-062**：书签用于快速收藏值得回看的文档块，可附个人备注，不另建独立注释功能；书签跟随文档或块，一个文档块允许绑定多个书签。（U44）
- **FR-063**：允许讲解 AI 读取用户的笔记、书签等阅读记录，以辅助讲解。读取不等于获得修改用户记录的授权。（U44）

2026-11-19 作者在 [D019](../../docs/work/2026/11/D019-block-bookmarks/task.md) 确认首版主动收藏以块为单位。同块可存多条，每条备注选填。逐文件阅读页提供逐条修改和移除，顶栏书签列表回访当前讲解。正式管理页面留到 UI 优化阶段。文档级关联用于 U45 所述的确认删块后降级。

U45 已认可下列更新规则，包括块删除后真正降为文档级关联、不绑定到第一个块；不扩大为尚未讨论的具体字段、页面或实现均已批准。

| 更新情况 | U44 原始方案 | U45 确认结果 |
| --- | --- | --- |
| 同文档块修改、ID 不变 | 书签保持不变，用户看更新记录后自行决定是否修改 | 支持；不自动改写用户备注，也不重新判断收藏意图 |
| 新增文档块 | 不影响既有书签 | 支持 |
| 原块删除、文档仍在 | 自动挂到文档，可具体绑到第一个块 | 保留在原文档，真正降为文档级关联，在文档顶部显示“原块已删除”；不把目标改成第一个块 |
| 整篇文档删除 | 变为未绑定，在管理页面展示缺绑 | 支持；保留书签正文、原文档路径及原块 ID 供用户辨认，不自动删除 |

沿用 FR-027 与历史增删改规则，拆分合并产生新 ID，原块在首版按删除处理，不增加语义迁移算法。U45 认可不因解析失败、文档暂时读不到或更新半途缺块就持久改变绑定；成功完成并校验的文档更新后再处理确定的删除，其间只提示定位暂不可用。此处确认绑定维护时机，不借此批准其他尚未确定的收尾实现细节。

作者明确阅读记录需要管理页面并展示缺绑；具体分几个页面、各管理项与重新绑定交互随页面设计确认。原话中“批准”未擅自解释成新的审批模块，也不借此恢复已合并的独立注释功能。

U45 已明确首版不做 AI 修改笔记／书签及其审批机制：Skill 告知 AI 只读、不修改这些记录，用户仍可在页面修改。按用户确认的确定性规则维护绑定属于程序维护，不是让讲解 AI 改写个人内容。作者明确接受该约定无法技术强制执行的缺口；普通本地文件加 Skill 约束不等于操作系统权限隔离，不能宣称能阻止拥有文件写权限的外部工具。

U45 要求用统一诊断与 AI 修复原则收敛异常设计，见[总入口 DC-004](spec.md#统一异常处理原则u45)。修复或重建讲解不授予 AI 修改个人笔记、书签的权限；不继续为每一种可能异常追加独立恢复流程。

## 可行性事实与取舍

静态网页可以用 JavaScript 实现书签、注释和理解标记；交互不是只有服务才能提供。关键区别在于保存位置和数据进入 AI 上下文的方式。

| 环节 | 自包含静态页 | 本机服务或 DSH 适配 |
| --- | --- | --- |
| 点击标记、填写注释、跳转书签 | 可实现 | 可实现 |
| 保存到浏览器 | 可用浏览器存储，但 file URL 行为不能作为跨浏览器可靠持久化保证 | 也可使用，但并非必须 |

## U73 · 复制文档块定位 v1（作者授权 AI 定稿）

依据：[作者 U73](../../../tasks/AR1-回甘首版需求设计/amendments.md)。本节是复制定位格式的单一规格；复制功能与后续答疑指南引用这里，不各自维护不同格式。U72 的字段候选由本节收敛，指南如何拆文件仍不在本次授权范围内。这里只制定规格，尚未实现复制或解析功能。

### 文本与字段

复制结果为标题 `Aftertaste 文档块定位` 加一个 JSON 代码块。采用标准 JSON 转义，由程序生成，用户不手填字段；选中文字仅作引用数据，不作为 AI 操作指令。以下是格式示例，占位提交在真实输出中必须替换为完整 Git 对象 ID：

```json
{
  "format": "aftertaste-block/v1",
  "document": "docs/aftertaste/current/backend/app/auth.py.md",
  "block_id": "k7m2x9qa",
  "source_commit": "<完整 Git 提交 ID>",
  "selection": "这里先完成校验，再调用应用服务。"
}
```

| 字段 | 规则与用途 |
| --- | --- |
| `format` | 必填，固定为 `aftertaste-block/v1`；使 AI 和未来工具识别格式，后续不兼容改动另升格式版本 |
| `document` | 必填，相对于存放本套 `docs/aftertaste/` 的目标项目根目录，使用 `/` 分隔，包含完整 `.md` 后缀；不复制机器绝对路径、浏览器 URL 或临时访问令牌 |
| `block_id` | 必填，既有 8 位小写字母数字 ID；与文档路径共同定位，不能只按 ID 全仓猜测 |
| `source_commit` | 必填，取当前所展示内容的完整源码提交 ID，不取操作时的 HEAD；用于核对与读取对应源码，不代表讲解文件本身的 Git 版本 |
| `selection` | 可选，用户在该块内选中的讲解原文；未选择则省略，不复制整篇文档，不把选择内容当作永久字符位置 |

用户在代码块外自由补充问题或修改要求；复制动作不自动编造用户问题，不默认授权改文档。该格式服务于单块复制；一次表达多个块的问题可粘贴多个定位，不增加首版跨块字符范围协议。

路径基准只定义此复制文本：它是已有目标项目根，不要求项目根等于 Git 仓库根。源码相对 Git 仓库的位置映射仍按 02 后续设计。接收 AI 使用用户已指定的项目上下文；多项目歧义时先确认目标，不能凭相同相对路径认定同一项目。不增加项目 UUID、用户绝对路径或远端仓库地址字段。

### 当前、历史与失效

- 当前阅读页复制 `current` 下实际文档路径；历史阅读页复制所展示的历史 before 或 after 文档实际路径，不把旧内容伪装为 current。历史路径已能区分记录和前后侧，故不额外复制记录 ID、侧别和时间；具体历史目录命名仍按历史存储设计决定。
- AI 读取指定文件，核对块 ID 与源码提交，再按文档元信息和镜像映射读取固定提交源码。行范围由该块的 `lines` 读取；不在复制文本里重复保存可推导的源码路径和行范围。纯讲解块同样能定位，不要求它具备 `lines`。
- 定位文本不是讲解快照。同一源码提交下讲解也可能被修订；没有选中文字时不能保证还原复制当时的讲解措辞，有选中文字时仅能保留被选片段。AI 应以实际读取内容作答，发现片段或提交不符时说明；不增加指纹、复制时快照或自动恢复机制。
- 路径、块或提交不可用时，给出具体缺失或不匹配信息；可搜索供用户核对的候选，但不能当作已确认目标直接修改。只有引用片段可用时，可以明确基于该片段解释，不能声称已查证项目实现。
- 从历史复制用于回顾当时内容，不因此授权修改历史；用户要修改当前讲解时需识别 current 中的实际目标，不能直接把历史路径当写入位置。用户对 current 的明确修订授权仍按 U72 处理，不新增重复审批。
- 导出页面如后续获准实现，应携带展示时的定位元信息；复制定位不赋予接收 AI 访问本地文件的权限，只有分享 HTML 的人不一定拥有原项目。文档损坏而无法取得必填字段时，走已有错误诊断与修复信息，不伪造正常块定位。

本次不决定笔记内部链接编码、书签存储或永久版本锚定策略；这些可以复用路径与块 ID 的身份概念，但不能直接把答疑复制载荷当作全部用户记录的数据模型。

### 后续实现的验收例子

1. 无选择时复制四个必填字段；有选择时加入 `selection`，中文、引号及换行经 JSON 转义后可正确还原。
