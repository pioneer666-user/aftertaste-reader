## 已确认要求

- **FR-007**：AI 写讲解前确认并固定一个 Git 源码版本，让后续代码变化可以与原版本比较，辅助定位需要更新的讲解。（U4）
- **FR-010**：一套阅读资料统一对应一个 Git 源码提交，不为同一套中的每篇文件讲解分别选用不同的源码版本。（U5）

- **FR-011**：AI 生成讲解时读取已确认提交中的源码；网页也展示该提交中的源码。工作区未提交修改不进入这一源码依据。（U6）
- **FR-012**：资料版本更新由用户主动发起，不自动触发；比较原提交与用户选定的新目标提交的差异，供 AI 修订讲解。目标默认当前检出分支的最新提交（HEAD），同时允许指定本地已有提交；开始更新时固定为确定提交，不随分支继续移动。（U6、U8）
- **DC-001**：底层能力不依赖 Skill、网页或 DSH 等上层业务；上层调用底层完成适配。该原则不指定语言或 DDD 实现框架。（U6）
- **FR-035**：每篇讲解文档顶部记录所依据的 Git 提交信息，结合镜像路径定位该提交中的源码；源码提交也作为阅读资料的源码版本依据。记录具体语法尚未确定。（U22）
- **FR-036**：首版维护一套当前阅读资料，不按每个源码版本复制整套文档到不同目录；此范围决定不授权删除已有资料，也不等于已决定更新记录的保留方案。（U22）
- **FR-037**：用户主动更新时，通过旧新源码提交的 Git diff 辅助修订讲解，同时考虑并更新受影响的其他讲解，明确说明更新了什么，供用户重点阅读变化。影响判断仍由 AI 负责，不要求程序证明语义影响完整。（U22，沿用 U7、U17）
- **FR-038**：每次更新完成后，当前整套文档直接反映此次更新后的内容，默认入口展示这一套完整资料；用户无需阅读或依次应用更新记录才能获得最新讲解。“最新”指用户主动选择并已完成资料更新的源码版本，不自动追随 HEAD。（U23，沿用 U6）
- **FR-039**：保留更新记录供用户回顾当时的源码变化及对应讲解。连续多次修改同一个文件后，仍可分别查看每次更新自己的前后差异；早期记录不能因后续更新而变成与当前最新版的比较。（U23）
- **FR-040**：目标版本是否适合此次资料更新，由讲解 AI 结合用户意图判断，程序不以祖先关系、分叉或版本新旧决定是否允许更新。允许选择历史提交作为本次目标，将其视为资料回退；这里的“新版本”表示本次目标，不要求提交在历史上较新。U27 替代 U26 的拒绝旧版本要求；U26 的相同提交限制本轮未明确撤销，不顺带扩大裁决范围。（U26—U27）
- **DC-002**：复杂的选择与内容判断交给能处理这些问题的 AI，底层提供工具；延续 U20 的机械工作交给程序的原则。此原则不等于取消已确认的结构、定位和覆盖校验，也不将 AI 判断宣称为必然正确。（U27）
- **FR-041**：保存每次更新涉及的受影响文档在更新前、更新后的完整 Markdown，以文档路径及块 ID 作为前后块匹配的主要依据。该保存范围不是每次复制整套资料，具体存储组织尚需确定。（U28 提出，U29 确认）
- **FR-042**：块对应的源码发生变化时，即使讲解正文未变，也判定该块有修改；不能只比较讲解正文。源码与讲解变化的具体视觉表达另行设计。（U29）
- **FR-043**：首版历史差异处理块的新增、删除、修改，不额外识别或展示拆分、合并关系。既有重新分块产生新 ID 的规则不变，比较时按旧块删除、新块新增处理。（U29，沿用 U18）
- **FR-044**：提供由用户使用的旧更新记录删除入口，避免只能积累、无法清理。默认时间范围、筛选依据与具体删除流程尚未确认；该需求不授权自动到期清理，也不授权当前删除任何历史资料。（U29）
- **FR-045**：首版每次更新记录独立保存本次受影响文档的前后完整 Markdown；回顾时不依赖下一条记录或当前文档取得比较两端。删除一条记录不破坏其他记录，不采用全局只留新旧两版、更新前删除旧版的方案。独立保存文档不等于已批准保存源码快照，具体编号、目录、排序与清理规则仍需确定。（U30）
- **FR-046**：仅同步文档顶部源码提交信息，源码、讲解及块结构等实际内容未变的文档，不因此进入本次更新记录，也不标为内容修改；当前文档的版本依据仍须与整套目标一致。该排除规则不免除 AI 对跨文件影响的判断。（U31）
- **FR-047**：当前各篇文档的源码提交字段由程序统一同步，不让讲解 AI 逐篇手工改写。同步在完成本次更新的步骤执行，不在更新开始时批量改成目标提交；不修改历史记录固定的前后版本依据。具体完成判据与中断处理另行确定，不把批量写入提交字段当作讲解已适配的证明。（U31—U32，沿用 U30）
- **FR-048**：更新按文档准备：同次更新首次修改前由程序保存原文，重复准备不得覆盖该原始副本；AI 直接编辑当前 Markdown，保留可读更新说明和前后文档供中断后接续，程序在完成步骤检查、同步版本并固定更新后文档。首版不建设逐块编辑器或逐操作日志；具体命令与异常收尾规则尚需设计。（U34 对主流程的认可）
- **FR-049**：更新说明采用固定格式及 Markdown 勾选清单，供 AI 表达处理进度、接续未完成工作，程序检查未完成项并警告。勾选不证明讲解正确，不替代结构、源码定位与覆盖检查；具体模板及警告是否阻止完成仍需确定，扫描范围遵循 FR-050。（U34—U35）
- **FR-050**：整次更新状态放在 history/<更新编号>/ 的更新说明中，current 不重复维护该状态。程序维护更新中与已完成，AI 维护工作清单；清单全勾不代替程序收尾。清单检查限定于模板指定范围，不扫描正文中的任意复选框。具体文件名与字段语法另行确定。（U35 认可上轮建议）
- **FR-051**：用户在更新尚未完成时要求更换目标，程序给出未完成警告，讲解 AI 承担向用户说明情况及选择后果的责任；不把先回退设为换目标的强制条件。提供回退至本次更新前资料的程序能力供用户选择，用户也可选择保留半成品继续更新。具体记录复用、回退范围及错误处理尚未确认，不据此取消既有校验或宣称失败操作成功。（U35）

版本粒度、读取来源、更新发起方及目标选择已确认；中间状态采取展示时检测并降级（见 02），具体记录格式与目标项目范围尚未决定。

U22 的逐篇提交信息不视为撤销 FR-010：完整可用的一套资料仍统一对应一个源码提交，文档头记录该依据，不让每篇自行选版。如何表示整套目标、如何处理更新中仍记录旧提交的文档，继续明确设计，不能默默把混用当成正常结果。

## 用户场景与验收草案

用户围绕版本 A 阅读并生成讲解；项目后来发展到版本 B。维护讲解时，AI 能确定原讲解依据 A，并比较 A、B 的源码变化，而非凭记忆重新猜测。

验收需要覆盖：

1. 生成讲解后，能够识别其依据的确定源码版本。
2. 后续源码变化时，能够区分原依据和新目标版本，并找到变化的文件或片段。
3. 资料绑定 A 后，即使工作区源码已经改变，AI 读取的源码与网页展示的源码仍来自 A。（覆盖 FR-011）
4. 同一套资料讲解多个文件或一条跨文件链路时，全部以同一个选定提交为源码依据。（覆盖 FR-010）

5. 仅产生新提交或工作区修改不会自动发起资料版本更新；用户选择更新到 B 后，比较的两端为 A、B。（覆盖 FR-012）
6. 完成 A→B 后直接打开当前文档，得到 B 的完整讲解；继续完成 B→C 后得到 C 的完整讲解，不需要用户从旧文档叠加更新记录。（覆盖 FR-038）
7. 两次更新修改同一个文件、甚至同一段代码后，第一次记录仍展示 A→B，第二次展示 B→C；不将第一次记录的右侧偷换为 C。（覆盖 FR-039）
8. 用户已读过某次更新，后来忘记时仍能再次打开其记录；具体标记交互与历史保留机制须按 U24 逐项确认。
9. 讲解 AI 根据用户意图选择历史提交或分叉提交作为更新目标时，程序不因其不是后继提交而拒绝；仍按确定的起点与目标比较。U26 的相同提交限制本轮未明确撤销，不据此禁止其他文档修复场景。（覆盖 FR-040）
10. 受影响文档的更新前后完整 Markdown 可用于按块比较；同一块讲解正文未变、对应源码发生变化时仍标为修改。重新分块造成旧 ID 消失、新 ID 出现时，首版按删除和新增处理，不要求推导拆分合并关系。（覆盖 FR-041—FR-043）
11. 完成 A→B、B→C 两次更新后，第一条记录使用自己保存的前后文档展示 A→B；删除第一条后，第二条仍有自己的前后文档可展示 B→C，当前 C 的完整资料不依靠第一条恢复。本场景以相应源码提交可读取为前提，源码快照方案尚未决定。（覆盖 FR-045）
12. 一套 100 篇文档更新时，若只有 3 篇出现源码、讲解或块结构等实际变化，其余 97 篇仅同步源码提交字段，则不因这 97 篇 Markdown 的元信息变化而为其保存历史前后全文；程序负责当前文档的提交字段同步，AI 不逐篇改写该字段，既有历史记录保持原依据。（覆盖 FR-046—FR-047）
13. AI 勾完清单但程序尚未成功收尾时，记录仍为更新中；正文示例含未勾选复选框时，不作为工作清单警告。状态只维护于 history 的更新说明。（覆盖 FR-049—FR-050）
14. 更新未完成时用户改选另一目标，程序提示未完成事实，AI 说明可先回退；用户选择保留当前半成品继续时，不因未先回退而拒绝更换目标。回退的具体数据恢复验收须在范围确认后补充。（覆盖 FR-051）

更新中断的展示策略已经确定，具体检测规则、跨文件影响和更新完成判据待定；以上不是实现验证结果。

## AI 建议（均未批准）

- 固定版本记录为不可混淆的完整提交标识，而非只记会移动的分支名；分支或标签可作为辅助显示。
- 文件内容变化先标为需要核验，不自动等同于整篇重写。只增加空行可能影响行号，但不一定改变解释；实际逻辑变化可能影响多篇讲解。
- 辅助记录文件内容指纹可用于识别变化，但不能用它单独证明跨文件解释仍正确。
- diff 给出变化证据，不单独证明未变文件的解释仍适用；可由上层 Skill 结合依赖和闭环判断影响，不预设必须开发复杂底层影响分析器。
- U8 已否决“临时生成整套资料、完成后统一切换”的候选，不再作为当前推荐。需要简单的版本或内容对应检查来识别中断遗留的问题，字段与判定规则待设计；格式合法不等于版本适配。

以上只是建议，不默认要求某种快照格式、状态机、自动检测服务或全量重生成。

## 当前完整资料与更新回顾（U22—U23）

作者强调更新场景的核心资产是变化及其讲解。U23 认可一套当前文档配合更新记录的方向，并明确：当前文档必须直接是 AI 更新后的完整最新版；更新记录用于回顾当时的 diff，不承担逐次拼装最新版的职责。首版优先基础建设；不由此自动扩展任意版本组合比较、整套旧版浏览或分支合并功能。

默认入口与历史入口应明确区分。更新记录需标明自己的旧、新依据，用户知道正在查看历史变化而非当前完整资料；本轮未确定具体页面布局。AI 建议理解标记不触发文档改写或历史删除；按 U24 只认可大方向的澄清，该具体交互不能仅依据 U23 对整体方案的认可视为已批准。

首版不复制每个版本的整套文档。U29 已确认保存受影响文档的更新前后全文；具体目录、字段与版本组织仍在讨论。U23 提出参考 Git，但不等于要求实现 Git 的分支、合并和冲突解决系统。连续更新同一文件本身属于历史演进，不等同于同时修改再合并的冲突。

设计事实：源码提交标识只定位该次提交中的文件。之后生成的讲解不一定包含在该源码提交中；只有实际保存过旧讲解，才能原样找回，重新让 AI 解释不保证恢复原文。若采用 Git 保存讲解历史，需要另行明确讲解提交与源码提交的对应关系及写入授权；当前不自动提交用户项目或新建历史目录。没有新增正式暂缓项。

U23 明确的是更新成功后的默认阅读结果，不恢复 U8 已拒绝的“临时生成整套资料后统一切换”机制。更新中断仍须明确暴露不适配，不能把混合状态冒称为最新版整套完成；完成判据与记录落盘流程继续讨论。

U24 要求先在本方向内深入细节，不直接进入下一层或产品实现。讨论使用具体阅读与更新场景，每项明确推荐、代价和确认范围；作者未确认的内容仍是建议，不自动登记为正式暂缓事项。具体 diff 保存方案不因认可“大方向”自动成为需求。

U26 调整当前讨论顺序：先从用户选择目标版本、比较当前资料版本、取得源码 diff 开始，讨论讲解 AI 如何执行更新以及如何生成更新记录，再决定历史页面展示范围。此前“仅展示变化片段”与“可展开历史完整文件”的选项均未获选择，不作为前置要求；本次没有新增正式暂缓项。程序保存旧讲解、生成差异与 AI 撰写变化说明的具体分工仍须讨论，不能从已有机械工作交给程序的原则推定全部流程获批。

U27 明确允许选择历史版本作为目标，由 AI 判断版本适用性，撤销 U26 的拒绝旧版要求；既有“最新完整资料”应理解为最近完成更新的目标资料，也可能对应较早的源码提交。用户提出“受影响文档前后全文保存”与“计算后只存 diff”两种候选，尚未选择。需区分独立展示当次差异与还原完整历史文档：前者可直接展示保存的差异内容，后者还需要完整依据及恢复方案；不能把只存 diff 自动等同于必须开发历史重建算法。

## 未决成功标准

U32 提出跨 AI 的中断续接场景；U33 要求 AI 以降低复杂度为优先主导方案；U34 基本认可按文档准备、原文不覆盖、直接编辑 Markdown 和程序收尾的主流程，见 FR-048，并明确清单警告机制，见 FR-049。保留的材料帮助识别差异和接续，不证明 AI 已完成语义检查；具体写入顺序、中断一致性与失败处置继续讨论。源码或讲解任一有变化都不能当作无变化取消。

U34 已明确当前资料位于 docs/aftertaste/current 下镜像源码，02 的路径示例据此更新；本轮不创建产物目录或迁移文件。历史按独立更新身份组织，具体命名未定；只把源码提交 B 作为记录目录名不足以区分重复到达 B 的多次更新。U35 明确已有未完成更新不构成拒绝换目标的理由；此前“一次一项”的建议不能成为阻止用户的硬限制，本轮推荐通过修改未完成记录的目标避免增加并行记录。

U35 已认可状态归属及程序与 AI 的分工，见 FR-050；不将上轮示意说明的全部字段或文件名视为定案。状态文件不可读或异常时不能据此宣称更新完成；具体异常行为与扫描格式后续明确。

## 更新中途更换目标与回退（U35）

已确认的原则见 FR-051：提示未完成情况、由用户决定是否先回退，程序不以已有未完成更新为由拒绝换目标。这里讨论的是同一套当前资料，不扩展为并行分支或自动合并系统。

**本轮 AI 推荐，尚未批准：更换未完成记录的目标，保留原起点与首次备份。** 例如 A→B 只完成了一部分，用户选择不回退而改向 C，则继续使用这一条未完成记录，将目标改为 C；记录原目标 B 和换目标事实，最初 A 的 before 不覆盖。最终完成的是 A→C，不把没有完成的 B 当作历史完整版本，也不另建以混合半成品冒充 B 起点的记录。未来完成后的下一次更新仍独立保存前后文档，不改变 FR-045。

换目标时，AI 必须重新检查“原任务已经动过的文件”以及“A 与 C 的源码差异及关联影响”，不能只检查 B→C，也不能只看 A→C 的变更文件。例如某文件在 A 与 C 中相同，却在更新到 B 的途中改过讲解，该文件仍需复核。原清单已勾选项不能直接当作对 C 的完成证明；具体清单调整方式仍需确认。程序继续负责差异、备份和结构检查，不自动判断讲解适配。

**回退能力的最小方案建议，尚未批准：** 仅撤销指定未完成更新对当前资料的修改，不切换用户源码的 Git 提交，不做任意历史版本恢复。准备文档时由程序记录“原来存在／原来不存在”：原来存在的恢复原文，本次新增的撤销，本次删除的恢复；重命名在首版可按删除与新增处理。回退会放弃这次更新中涉及文档的后续编辑，需向用户明确说明。恢复成功后保留记录并标明已撤销，而非标为已完成或静默删除；状态名仍是建议。缺少必要备份时必须报告无法完整恢复，不能凭空重建原文并宣称成功。

本方向尚需落实的细节：收尾多文件写入中断后如何重试、回退如何处理已同步的文档头，以及准备步骤被绕过时可保证的恢复范围。这些是本轮明确提出的讨论问题，不是新增正式暂缓项。当前完成资料统一版本的规则不变；未完成内容即便语法合法也不能冒称已经适配目标版本。

U30 已确认独立保存前后文档、不依赖下一条记录及删除互不破坏的组织原则，见 FR-045。以下仍是未批准的 AI 建议：每次记录设置独立身份、完成时间、起点及目标源码提交，按完成时间排列列表。具体字段、排序规则与目录仍需确认。源码是否额外保存仍未决定，Markdown 全文不包含左侧源码，不能据此宣称脱离原 Git 仓库也可完整回顾。

清理建议尚未批准：用户主动发起，默认筛选完成时间距今超过 30 天的记录，可选择其他范围；先显示候选及占用，再由用户选择删除。不将时间较早等同于用户很久未阅读，不新增访问追踪。30 天是针对本产品的建议，不是行业统一标准。

参考依据（2026-11-15）：[Git diff](https://git-scm.com/docs/git-diff) 支持直接比较指定的两个提交；[restic 历史清理](https://restic.readthedocs.io/en/stable/060_forget.html) 提供按 ID 删除、按保留策略筛选和预览。以上支持分离比较依据与清理策略的设计思路，不表示采用其全部存储机制或固定保留天数。
