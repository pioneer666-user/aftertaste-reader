## 要解决的问题

把已生成的讲解、对应源码与定位信息提供给网页阅读器。先确认用户怎样打开、怎样更新，再比较实现技术。

TypeScript 与 JavaScript 是语言选择；使用原生页面还是框架是另一个选择。它们不是三个互斥方案，TypeScript 也可以配合原生页面或框架。

## 先讨论运行方式

以下保留方案演进。当前以 U9 比较为准：目录授权方案保留为研究记录，不再作为首版推荐。

| 候选 | 用户怎样使用 | 需要承担的代价或限制 |
| --- | --- | --- |
| 预先生成静态阅读页 | 生成后直接打开，阅读时不需要本地服务 | 内容变化后要重新生成；文件打开方式对读取和浏览器能力有限制，需要设计并验证 |
| 固定阅读页＋用户授权目录 | 用户通过浏览器选择目录，页面从授权目录重新读取 Markdown 和阅读数据 | 需要支持目录访问 API 的浏览器；授权恢复、file URL 打开方式需验证；不能直接调用本机 Git 命令 |
| 启动本地阅读服务 | 启动服务后用浏览器阅读，由服务提供项目资料 | 多一个运行与关闭步骤，需要规定端口、路径访问及文件写入边界 |

浏览器页面不能凭一个本地路径随意读取整个项目。因此无论选择哪一种，都要明确资料由谁准备、网页读取什么；不能只写“网页直接打开 Markdown”就认为数据通道已经解决。

可将网页资源、讲解和对应源码预先生成在一起，也可由本地服务提供；当前没有作出选择。

## U6 后的运行方式比较（建议，未裁决）

本地服务同样可以离线工作。这里真正比较的是“双击预生成页面”与“启动本机服务后打开页面”，不是离线与联网。两者都能实现代码高亮、双栏对照、依赖图、动画和选中文本；服务本身不提高视觉效果。

| 使用情形 | 预生成页面 | 本机服务 |
| --- | --- | --- |
| 阅读已有资料 | 预先打包所需资源与内容后，直接打开 | 需启动进程，再打开本机地址 |
| AI 新增或用户修改 Markdown | 需重新导出受影响的阅读内容，再刷新；不是重新让 AI 写讲解 | 服务读取更新后的文件，页面刷新即可；自动刷新仍是额外功能 |
| 读取 Git | 导出脚本读取已确认提交，页面消费结果 | 服务端可读取已确认提交，页面消费结果 |
| 从页面保存项目文件 | 需要另行设计授权文件访问或导出机制 | 可通过受限的本机接口写入，但不能把此能力默认列入首版 |
| 大量资料 | 整包或分页打包有大小和加载成本，需具体方案 | 容易按需读取；性能仍取决于实现与规模 |
| 使用成本 | 阅读免服务；生成/导出仍可能需要运行环境 | 需要运行环境、启动与关闭约定；可封装启动命令 |

上一轮建议优先考虑导出页面；U8 追问后已补充目录授权方案，因此该建议不足以直接裁决。现在需比较浏览器范围、授权体验和 Git 源码交付方式，再选择运行方式。

浏览器 file URL 存在同源及资源读取限制，不能假定双击 HTML 后能随意 fetch 项目文件。复制功能也有安全上下文、用户操作和浏览器差异，需针对最终运行方式验证，并考虑手动复制后备方式。

依据（2026-11-14 查阅）：[MDN 同源策略](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)、[MDN Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API)。这些资料支持浏览器限制事实；方案取舍是本项目的设计建议。

## U8 · 不启动服务也能重新读取的条件

纠正此前比较不完整之处：不能凭路径任意 fetch 本地文件，不等于不能通过用户授权读取文件。File System Access API 可让用户选择目录，再通过目录和文件句柄读取内容；文件变化后重新取得 File 对象即可读到更新内容。桌面 Chrome、Edge 可作为候选目标，不能假定所有浏览器均支持。

应区分页面内“重新读取”与浏览器 F5：前者可沿用当前目录句柄；后者需要恢复句柄并检查权限，必要时用户重新授权或选择目录。不能保证跨会话永久免授权。file URL 可属于安全上下文，但这不等于特定浏览器下目录选择、存储和权限恢复全部经过验证；本项目尚未做浏览器实测。

候选使用流程（尚未批准）：

1. Skill 使用本机 Git 读取已确认提交，准备对应源码快照和必要索引；具体文件格式及目录待定。
2. 用户打开固定的阅读器 HTML，点击选择资料目录并授权只读访问。
3. 页面读取最新 Markdown 和与目标提交对应的源码快照，完成对照。
4. AI 或用户修改 Markdown 后，点击页面的重新读取即可，不必重新导出 HTML。
5. 用户更新源码目标提交时，再由脚本更新源码快照和相关资料；不能把工作区当前源码当作已确认提交源码。

目录授权只提供文件访问，不提供启动本机 git 命令的能力。自行在浏览器解析 Git 对象是另一项工程，不作为首版默认方案。本机服务若只提供静态文件，也仍需提前准备源码快照；只有专门实现了 Git 接口的服务或宿主才能按需读取提交源码。

即使选择导出，也不必每次生成一个不同 HTML：可复用阅读器资源，仅重建数据或覆盖同一份阅读页，具体方式需服从浏览器加载限制。

本地证据：旧插件 specdev-workbench/src/dsh/index.ts 引入 node:fs/promises，并在 serveFile 中 readFile 后通过 HTTP 响应输出；它借用了 DSH 的服务端运行能力，不是普通网页直接按路径读取电脑文件。这里只核查相关路径，未审计 DSH 全部文件访问实现。

参考：[Chrome 文件系统访问说明](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)、[MDN showDirectoryPicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)、[MDN 安全上下文](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)。查阅日期 2026-11-14；浏览器适配仍属待验证事项。

## U9 · 单文件导出与本机服务的完整比较

作者优先考虑安装简单、打开方便、可分享，以及不累积旧 HTML。作者在表达导出选择后继续要求比较并再决定，因此当前记为倾向，不提前冻结运行方式。

### 已确认的导出保留原则

- **FR-017（选择导出时适用）**：每套资料更新同一个导出 HTML，默认不保留多份历史导出。具体文件名与位置尚未定；保留 Markdown、阅读器程序等既有资产，不擅自清理用户另存文件。（U9）
- AI 建议：先写完本次导出再替换上次成功文件，失败则保留上次成功文件。这是单个输出文件的写入保护，不重新引入 U8 已拒绝的整套文档事务；尚未确认。
- 现有打开页面需刷新才显示替换后的文件；已经分享出去的副本不会随本地导出更新。

### 运行与维护取舍

| 维度 | 自包含的单文件 HTML | 本机阅读服务 |
| --- | --- | --- |
| 阅读者准备 | 获取文件，浏览器打开；所需资源内嵌后可断网 | 运行服务程序，再打开本机地址；可封装一键启动 |
| 生成者准备 | 仍需能运行导出工具及 Git，Skill 本身不会消除运行环境要求 | 需运行服务及读取提交源码所需环境，可与生成工具复用 |
| 修改 Markdown | 再导出后刷新；导出仍直接复用已有 Markdown，不让 AI 重写 | 刷新时按需读取、解析最新 Markdown；自动刷新需要另行开发 |
| 分享 | 发出一个包含所需源码和讲解的文件即可离线阅读 | 发 localhost 地址给合作者无效；需对方运行资料包或另外提供导出/部署 |
| 大资料集 | 整个文件携带全部内容，打开和解析成本随体积增长 | 可以按需读取当前文件，初始打开成本较容易控制 |
| 磁盘 | 讲解原件之外多一份打包数据；覆盖旧文件可避免历史累积 | 不必复制整包阅读数据，但仍有运行程序、依赖或快照的成本，不保证总占用更小 |
| 页面操作项目文件 | 无桥接、授权或服务时不能静默写回项目 | 可实现受限读写接口；不是启一个服务就自动拥有所有业务功能 |
| 实现成本 | 数据采集、验证、内嵌与转义、导出失败处理；阅读时不管理进程 | 读写接口、Git 访问、缓存更新、端口、启动关闭及路径边界 |
| 页面效果 | 代码高亮、双栏、目录、图形和交互均可做 | 同样可做，服务本身不提高视觉表现 |
| 浏览器适配 | 可避开目录选择 API，但复制、本地存储等仍需兼容处理 | 可避开 file URL 限制，但仍需常规浏览器适配 |

服务不限定 Node.js：Python 等也可提供 HTTP 服务；Node 应用也能打包为无需另装 Node 的独立程序。代价是平台和架构发行包、程序体积及维护成本。不能用“必须安装 Node”作为服务方案必然劣势，也不能宣称导出工具天然无需环境。

静态文件服务不自动提供 Git 查询或 Markdown 转换。即使采用服务，也需要实现本产品的读取与解析逻辑；源码必须继续取选定提交，不能直接读取当前工作区替代。

### 启动与导出耗时的证据边界

当前没有 aftertaste-reader 实现，未启动服务、未进行导出性能测试。不能给出实测秒数，也不以本次读取文件命令耗时充当产品性能。

耗时应分别记录：

- 服务：进程启动到可响应；以及浏览器打开到当前文档可读。首次安装或下载不能混入每次启动时间。
- 导出：已有 Markdown 与确定提交开始，经 Git 读取、校验、打包到成功替换输出；不包括 AI 生成讲解的等待时间，也不默认每次重建前端程序。
- 设计讨论中的量级预期：预构建轻量服务应以亚秒到数秒启动为优化方向；几 MB 文本资料的导出应以几秒内为目标。两者均不是实测、既定验收指标或对任意机器的承诺，较大项目可能明显更慢。
- 后续如作者批准小范围验证，应选固定提交和已生成文档，分别记录体积、耗时和首次可读时间；不需要先实现完整产品。

当前 AI 推荐：首版优先单文件导出、固定输出位置、复用预构建阅读器，日后 DSH 提供实时读取适配。核心原因是用户重视免服务阅读与分享；不是因为服务天然慢或无法免装 Node。是否最终采用，等待作者在比较后裁决。

依据：[Node 独立可执行应用](https://nodejs.org/api/single-executable-applications.html)、[Python HTTP 服务](https://docs.python.org/3/library/http.server.html)。查阅日期 2026-11-14；成本比较及性能目标是 AI 设计判断，未经过产品验证。

| 候选 | 可以讨论的理由 | 尚需明确 |

## 仍需补齐的使用边界

- 支持的操作系统、浏览器与屏幕范围；不能直接把巧格原型的电脑端限定视为本项目已批准范围。
- 普通使用者是否需要安装运行环境，是否需要自己执行构建。
- 页面已确定显示选定提交源码；如何将它交付到页面、是否保留可重建快照待定。
- 文档更新后由谁触发构建或刷新；显示时不适配的降级行为已由 02 的 FR-016 确认。
- 复制定位在目标打开方式下怎样工作，复制失败怎样继续使用。
- Markdown 中的链接、图片、代码块与原始 HTML 支持范围。
- 项目资料是否保持本地、哪些操作会访问网络；与后续 DSH 接入边界如何区分。
- 单份文件和资料总量的可接受规模；性能数字须有目标场景依据，不填模板默认值。
