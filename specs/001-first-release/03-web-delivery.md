# 03 · 网页承载与技术选择

状态：全部方案待讨论，未选择语言、框架或运行方式。依据：[作者 U4](../../../tasks/AR1-回甘首版需求设计/amendments.md)。返回[总入口](spec.md)。

## 要解决的问题

把已生成的讲解、对应源码与定位信息提供给网页阅读器。先确认用户怎样打开、怎样更新，再比较实现技术。

TypeScript 与 JavaScript 是语言选择；使用原生页面还是框架是另一个选择。它们不是三个互斥方案，TypeScript 也可以配合原生页面或框架。

## 先讨论运行方式

| 候选 | 用户怎样使用 | 需要承担的代价或限制 |
| --- | --- | --- |
| 预先生成静态阅读页 | 生成后直接打开，阅读时不需要本地服务 | 内容变化后要重新生成；文件打开方式对读取和浏览器能力有限制，需要设计并验证 |
| 启动本地阅读服务 | 启动服务后用浏览器阅读，由服务提供项目资料 | 多一个运行与关闭步骤，需要规定端口、路径访问及文件写入边界 |

浏览器页面不能凭一个本地路径随意读取整个项目。因此无论选择哪一种，都要明确资料由谁准备、网页读取什么；不能只写“网页直接打开 Markdown”就认为数据通道已经解决。

可将网页资源、讲解和对应源码预先生成在一起，也可由本地服务提供；当前没有作出选择。

## 再比较开发技术

| 候选 | 可以讨论的理由 | 尚需明确 |
| --- | --- | --- |
| 原生 JavaScript | 依赖较少，简单阅读页可以直接组织 | 交互状态增多时如何维护 |
| TypeScript 配合原生页面 | 为源码定位、文档与阅读状态等数据提供类型检查 | 增加构建步骤，如何交付可直接使用的成品 |
| TypeScript 或 JavaScript 配合框架 | 组件与复杂交互状态有现成组织方式 | 框架依赖和构建是否值得；具体框架尚未比较 |

当前不推荐或锁定具体框架。语言与框架的最终选择依赖前两分册的数据约定及本分册的运行方式。

## 仍需补齐的使用边界

- 支持的操作系统、浏览器与屏幕范围；不能直接把巧格原型的电脑端限定视为本项目已批准范围。
- 普通使用者是否需要安装运行环境，是否需要自己执行构建。
- 页面显示基准版本的源码还是当前工作区源码；对应 01 的版本一致性问题。
- 文档更新后由谁触发构建或刷新，更新失败如何表现。
- 复制定位在目标打开方式下怎样工作，复制失败怎样继续使用。
- Markdown 中的链接、图片、代码块与原始 HTML 支持范围。
- 项目资料是否保持本地、哪些操作会访问网络；与后续 DSH 接入边界如何区分。
- 单份文件和资料总量的可接受规模；性能数字须有目标场景依据，不填模板默认值。
