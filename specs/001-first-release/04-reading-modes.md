## 用户场景与验收

两个场景均为首版必需；开发顺序未定。下列验收场景是对 U3 的展开，细节须继续确认。

### 场景一：从基础文件逐步深入（M1）

**用户价值**：先理解后续文件所依赖的内容，再继续读更上层的文件。

**已确认过程**：用户明确范围 → AI 按依赖与难度选择起点，组织相关小批次 → 生成各文件对应讲解 → 按用户意愿连续生成后续批次，或等待用户逐批阅读后再继续。阅读反馈可供 AI 按需参考，不以已理解作为继续条件。（U52、U55、U56）

**独立验收例子**：给定一个小项目，B 依赖 A，C 依赖 B，且 A 不依赖其他项目文件。核对推荐顺序是否为 A、B、C，并核对每份文件进入阅读前是否已有对应讲解。

**验收场景**：

1. 给定上述 A、B、C 依赖关系，开始 M1 时，起始阅读对象是 A。
2. 给定 A 已读完且 B 是下一份阅读对象，进入 B 的阅读前，AI 已生成 B 对应的讲解文档。
3. 给定已有阅读反馈，AI 可结合反馈及依赖关系安排后续批次；用户明确要求全部生成时，可在确定范围内分批连续生成，不要求每批先读完。

“已读完”如何记录以及用户能否跳读仍需讨论；U56 已明确按关联组织小批次，用户可选择连续生成全部或逐批阅读后再生成，不能把逐文件已读完当成所有生成方式的前置门槛。

### 场景二：沿完整链路逐个理解（M2）

**用户价值**：围绕一个完整过程连续理解各步骤，形成前后联系。

**已确认过程**：找最简单的完整闭环 → 沿链路逐步阅读并查看对照 → 再阅读后续闭环。

**独立验收例子**：使用一条已核实存在的简单完整链路，核对其步骤是否前后衔接、是否覆盖该链路的结果，以及各步骤是否均能查看对应源码与讲解。

**验收场景**：

1. 给定项目中存在多条完整链路，M2 从最简单的一条开始；“最简单”的判定标准待确认后补齐验收依据。
2. 给定已选链路，每一步提供对应源码与讲解，且步骤前后能衔接。
3. 给定当前闭环已读完，能够继续下一个闭环；完成判据和后续选择规则待讨论。

该模式不预设必须读完整个文件，也不预设跳过其余源码；展示粒度待作者裁决。

### 边界情况（未决）

- 多个文件同时满足起读条件，如何选择或让用户选择。
- 文件相互依赖、无法直接进行拓扑排序时如何安排阅读。
- 动态依赖、运行时注入、外部库等是否属于 M1 的排序依据。
- AI 未找到足够证据证明链路完整，或存在多个同样简单的闭环时如何处理。
- 已读文件出现在后续闭环中，如何复用讲解和处理阅读状态。
- 阅读中源码变化、文档不存在或生成失败时如何继续。

以上不是已批准功能清单；用于后续补齐规格，当前不指定解决方案。

## 需求

### 已确认功能要求

- **FR-001**：首版提供 M1 与 M2 两种模式。（U3；场景一、二）
- **FR-002**：M1 从不依赖其他项目文件的基础文件开始，按依赖关系安排阅读先后。（U2、U3；场景一）
- **FR-003**：M1 由 AI 按依赖关系组织相关小批次，结合用户选择的节奏推进；支持逐批阅读后再生成，也支持用户明确要求在已确认范围内按批连续生成全部。已有阅读反馈可按需参考，不以已读完或已理解作为连续生成的前置条件。（U3、U56；场景一）
- **FR-004**：M1 进入文件阅读前，AI 生成该文件的讲解文档；一批可生成一个或多个文件的文档，不改变逐文件镜像存放规则。（U3、U56；场景一）
- **FR-005**：M2 从最简单的完整闭环开始，逐个闭环组织阅读。（U3；场景二；简单与完整的判据未决）
- **FR-006**：M2 的链路前后逻辑连贯，每一步都有源码与讲解对照。（U3；场景二）

### 关键概念（仅概念层，未定存储结构）

- **文件**：M1 中逐份阅读的源码对象。
- **依赖关系**：决定 M1 阅读先后的关系，由 AI 识别和处理（U52）；具体范围默认规则仍需确认。
- **讲解文档**：阅读前由 AI 生成，与源码建立对照的内容。
- **闭环链路**：M2 中完整、连贯的阅读对象，由多个步骤组成。
- **链路步骤**：提供源码与讲解对照的一个环节；定位粒度待定。
- **阅读状态**：支持安排后续阅读的信息；完成判据、记录方式及模式间是否共享待定。

## 成功标准

- **SC-001**：A → B → C 的基础依赖示例中，M1 阅读安排符合先基础、后使用者的顺序；每份文件进入阅读前有对应讲解。（覆盖 FR-002—FR-004）
- **SC-002**：M2 的样例完整链路中，每个步骤均有对照，读者可以沿步骤查看从起点到结果的过程。（覆盖 FR-006）
- **SC-003（待补齐）**：M1 能按用户选择逐批阅读后生成或分批连续生成，不能在连续生成时强制等待理解确认；阅读进度记录及 M2 推进判据仍需补齐，闭环选择应符合作者确认的规则。（覆盖 FR-001、FR-003、FR-005）

这些是局部验收场景，尚非完整首版验收清单；不以“AI 已生成文档”自动认定“用户已理解”，理解自评及不阻碍阅读的规则已在 05 确认。

## AI 建议与待讨论项

以下内容没有进入已确认功能要求：

1. 名称采用“依赖递进”“闭环串读”。
2. M1 的阅读依赖图统一使用“被依赖文件 → 使用它的文件”的箭头。例如 B 使用 A，画 A → B；这样 A 的入度为 0，与作者描述一致。若采用通常的“使用者 → 依赖”画法，起读文件应看出度为 0，不能混用。
3. 阅读推进可以理解为更新剩余可读对象；U52 已将依赖识别和阅读安排交给 AI，不要求程序重新扫描并计算语义依赖，也不承诺每次全量分析。AI 何时补充或复核关系仍需结合流程设计。
4. 两种模式尽可能共用源码、讲解与定位资料；共享粒度、内容差异和模式切换后状态如何处理尚未决定。
5. 将阅读顺序与讲解深度分开讨论。M2 也可以细致讲解，不能仅凭模式名称就自动缩减内容；具体深度与控制方式待确认。

基础设计讨论完成后，再继续 M1 的“读完”判据与多候选选择、M2 的“简单”“完整”定义和逐步对照粒度。其余首版功能另行讨论，不从既有巧格阅读器自动继承。

## U46 · 闭环作为文档之间的阅读路线（作者设想）

来源：[作者 U46—U47](../../../tasks/AR1-回甘首版需求设计/amendments.md)。U46 最初为设想；U47 已确认路线、讲解、记录的大方向，以及从已完成的文档图找闭环、由用户选择后再串讲。其余具体候选仍未批准，不新增正式暂缓项。

作者提出：文件讲解逐步积累，覆盖一条完整业务链路后，再把全链路串起来讲；也可以主动挑选一个闭环，讲解、阅读、提问、理解后再进入下一个。闭环与文件讲解分开，是文档图中的一条路，可有独立目录、数量按用户需要决定。后端创建表单是其举例，实际项目链路尚未核查。

作者希望资料更新不自动改写闭环：发现影响先告知，用户按需逐个更新和重学。学习过程可追加记录，文档更新后不自动删除旧记录，用户愿意可回看或删除；AI 可读取过去的疑问和学习经历来调整教学，但不把旧记录当成当前源码事实或据此自行改文档、代码。具体保存内容、目录、版本绑定及影响检测尚未裁决。

U46 的 AI 建议及 U47 确认边界：

- 将闭环内容分为有序路线、串联讲解、学习记录：U47 认可该内容形态。路线定位已有文档块；具体讲解方法、记录内容与格式仍需后续设计。文件讲解复用、不为每条路线复制整篇文件文档仍为配套建议。
- 阅读依赖图与业务执行链路不同。业务路线可能返回同一文件、经过多个块，不能只按文件依赖箭头自动得出；让 AI 根据真实源码组织步骤，不要求先开发自动路径推导算法。
- 首次可用“一个业务动作从触发到可观察结果”界定范围。例如创建表单从接收请求、校验、处理、写入到返回结果；实际步骤须查证，不把创建、更新、查询全塞进第一条路线。关键失败分支按理解主流程所需带到，不预设遍历全部分支。
- U47 已将当前闭环流程收敛到已有文档图；此前“先选闭环再补齐缺失文件文档”不作为已批准流程。发现资料不足不能冒称完整闭环，具体提醒方式不在本轮展开，也不自动扩展补齐流程。
- 路线及串联讲解应标明依据的源码版本。引用目标发生变化时提示需复核，由用户决定更新；保留旧讲解时不能无提示混接当前块冒充同一版本。具体是否固定历史内容仍需设计，不默认复制整套快照。
- 首版优先考虑保存必要的学习摘要和明确问题／回答，而非承诺自动抓取任意外部 AI 的完整聊天记录。究竟记录原文还是摘要、由谁写入，需要作者选择；不把学习记录等同于 AI 可改写的个人笔记、书签。

## U47 · 闭环方向确认

- **FR-068**：在已经做好的文档图中寻找完整业务闭环，供用户选择一条后，由 AI 沿该路线串联讲解；内容形态采用路线、讲解、记录。不是在技术依赖图中寻找图论意义的环，也不预设自动寻路算法。用户选择明确，不把“从简单闭环开始”的原则实现成程序强制排序。（U47）
- 具体 AI 怎样讲、参考哪些教学资料，需在后续 Skill 设计中结合资料检索及真实使用反馈改进，不仅凭当前讨论定成固定教学套路。本轮没有开展教学资料研究或试用，不声称讲解效果已验证。
- 作者提到“架构图”是在回应路线方向，不据此新增可视化架构图编辑器或图布局引擎。目录、记录格式、版本变化提示等旧候选没有因认可大方向而一并通过。

## U52 · AI 负责依赖识别与阅读安排

已确认分工：

- 由 AI 阅读指定 Git 提交的源码，识别和处理文件依赖关系，安排阅读先后；首版不为此自建多语言依赖解析设施。普通文件读取、搜索等工具不等于程序自行判断依赖语义。
- 起点优先考虑简单且不依赖项目内其他文件的文件；“简单”由讲解 AI 结合实际内容判断，不要求复杂度打分公式。
- U55 已明确阅读范围由用户选择：Skill 先询问并等待用户明确范围，不设置未回复后的自动起步范围。AI 负责在确定范围后识别依赖及安排阅读，可以推荐范围但不能代替用户选择。

AI 审视：该分工能减少本项目维护语言解析规则的负担，但不证明 AI 分析更准确或总耗时更低。没有发现依赖不等于已经证明不存在依赖；无项目内依赖也不等于容易理解。此处是能力边界说明，不增加自动分析引擎、置信度评分或新的审批流程。

此前提出未指定范围时由 AI 推荐并起步，U55 已改为先询问并等待用户选择，不继续沿用自动起步建议。区分查证依赖源码与生成讲解的范围，避免选择子目录后把其对项目其他目录的依赖误当成不存在，具体见下方 U55。不承诺未全面分析就找到了全项目最简单的文件；范围确定后的分析及首轮生成规模继续讨论。

## U53—U54 · 第三方解析工具作为 AI 的可选辅助（已确认）

U53 作者提议在 Skill 中推荐 AI 借用第三方语法解析器，避免自己实现复杂分析；U54 认可可选辅助的指导方式。AI 仍负责依赖判断和阅读安排，不将 U52 的 AI 主导理解为禁止 AI 使用工具。具体工具选型和安装命令未定，不设置首版必备解析器。

能力依据：[Tree-sitter 官方介绍](https://tree-sitter.github.io/tree-sitter/)说明它生成源码的具体语法树；[Python ast 文档](https://docs.python.org/3/library/ast.html)定义函数、导入等语法节点。这些结构可辅助发现声明及导入，但从导入名称定位实际项目文件、判断运行时依赖和阅读先后仍需进一步分析。Understand-Anything 的额外各语言解析规则也说明仅引入语法树工具不等于自动获得完整依赖关系。

U54 已确认：Skill 推荐 AI 按项目语言和环境选择合适的现有解析工具，优先复用可用工具，不设置必须安装某一解析器的前置条件；工具不可用或结果不完整时，AI 可回到源码和搜索继续分析，如实说明局限，不能把失败当作“无依赖”。工具分析仍以已选提交的源码为依据，首版不自行维护多语言解析器。没有因此引入内置安装管理、跨语言统一适配或修复第三方解析器的要求；未来若改为必需运行依赖，应另行讨论其兼容和维护成本。本轮未安装或运行解析器。

## U55 · 首次阅读先明确范围（已确认）

- Skill 流程先向用户询问阅读范围，等待用户明确后再开展依赖该范围的分析和讲解生成。用户未回复不等于授权采用 AI 推荐范围，不以超时或猜测自动开始。
- 用户可以选择项目中的目录或模块等范围。AI 可说明候选及理由，但阅读范围以用户选择为准，不默认整仓精读。

## U75 · 阅读方向资料最小模板（作者授权 AI 定稿）

依据：[作者 U75](../../../tasks/AR1-回甘首版需求设计/amendments.md)。本节落实 U58、U70，唯一模板保存在这里，后续 Skill 引用。本轮不创建实际用户阅读方向文件，也不改变已确认的范围、节奏与两种阅读模式。

### 模板正文

```markdown
# 阅读方向

## 已讲内容摘要

暂无已完成的讲解。

## 后续方向与理由

- 建议方向：尚未形成。
- 安排理由：尚未形成。
```

空模板不等于已分析项目，不能把计划中的内容填成已讲。形成真实内容后替换占位文字；不要求首次列出完整路线或所有未来批次。

已讲摘要按有助于后续衔接的主题组织，每个主题使用以下形式；不逐文件创建一条：

```markdown
### <已讲主题>
- 已讲到：<说明过哪些概念、讲到什么层次；必要时指出尚未串起的关系>。
- 代表文档：<一处或少量实际讲解文档的项目相对路径；需要精确定位时附块 ID>。
```

代表文档按需填写，不强制每个主题都列；必须是实际存在且确有相关讲解的资料，不伪造路径或引用。路径与块 ID 沿用既有定位规则，不在摘要中复制完整 JSON 定位载荷。摘要表示已经讲过什么，不表示用户读过或理解；“讲过用途，尚未讲调用链”比笼统的“已完成认证模块”更有助于下一批安排。

后续方向用以下形式填写；有必要时增加衔接重点，没有则省略：

```markdown
- 建议方向：<接下来适合阅读的概念、模块或业务方向>。
- 安排理由：<为什么接在前文之后，依赖或学习上的联系是什么>。
- 衔接重点：<后续适合串起的已有概念或尚未说明的联系，可选>。
```

方向可以用一两句话包含较远的路线，但不排满未来文件与批次，不加入待办勾选框、完成率或调度状态。AI 在实际生成前结合所选提交源码、现有文档和用户当前要求决定具体分组；本资料提供安排理由，不替代分析和用户授权。通常保留当前最有帮助的后续方向，非必须罗列多条候选。

### 假设示例

以下仅说明填写方式，不声称已分析作者项目、已有相关文档或已获得用户反馈：

```markdown
# 阅读方向

## 已讲内容摘要

### 表单输入与校验
- 已讲到：输入字段的含义与校验规则，解释了哪些无效输入应被拒绝；尚未串起校验通过后的保存过程。

## 后续方向与理由

- 建议方向：阅读使用这些输入约定的应用服务，理解表单创建怎样被组织起来。
- 安排理由：前面已介绍输入和约束，接下来查看它们的使用者，可以衔接基础定义与实际业务行为。
- 衔接重点：说明校验结果怎样进入后续处理，以及各层分别负责什么；等已有文档覆盖完整链路后，再推荐创建表单的闭环供用户选择。
```

### 维护与边界

- 每批完成后检查，有变化才合并修订；无需机械新增主题、批次记录或更新时间。相近主题合并，早期细节概括，保留衔接需要的层次和必要定位，具体内容回文档查。未完成的讲解不能因计划已写入就记为已讲。
- 后续方向随新讲解及用户要求调整，保留当前有用的安排理由，不追加历次计划变更流水账；这不授权删除任何讲解原文、更新历史或用户记录。
- 阅读范围与生成节奏以用户实际授权为准；写入建议不扩大范围，不授权连续生成，不把闭环候选当成用户已选择的闭环。U78 已确认节奏缺失时询问，不能靠模板填值绕过。
- 偏好资料负责怎样讲，块标记负责哪里不理解；本资料不复制这些数据，也不以“已讲到”代替用户自评。衔接重点只记教学联系，不积累全部局部问题或用户问答。
- 这是一份规划摘要，不是当前文档覆盖清单或源码版本的权威记录。继续讲解时仍核对实际文档及固定提交；内容或引用过时就据实修订，不能只凭旧摘要断言当前资料仍覆盖同样内容。不为该模板单独增加版本副本、完整状态索引或自动迁移机制。

具体文件路径与其他用户资料的统一目录、闭环自身的路线／讲解／记录格式不由此模板决定；它们仍按原设计问题继续讨论，不新增正式暂缓项。本轮模板可直接定稿，不需要先决定上述接口，也未证明真实教学效果。

## U82 · 确认依赖图语义，讨论存储位置与格式

来源：[作者 U82](../../../tasks/AR1-回甘首版需求设计/amendments.md)。作者认可 U81 后续提出的文件依赖图方案，明确保留连线上说明依赖原因的文字。一个节点表示一个源码文件，关系表达有源码依据的直接依赖；箭头采用“被依赖文件 → 使用它的文件”。不把纯教学先后或间接关系冒充直接依赖，不把箭头理解成请求执行顺序；允许环，未连线不能证明没有依赖。U81 中关于这些定义的“未确认”是历史状态，以本节确认为准。

以下为 AI 本轮存储建议，尚未得到作者确认，不作为实施协议，也不新增正式暂缓项：

后续状态：U83 已确认下列依赖图存储方案；本节保留提出时的状态。具体维护命令仍在 U83 中讨论，不能将存储结构认可扩大为全部写入接口获批。

- 使用一个 UTF-8 JSON 文件，建议路径为目标项目的 `docs/aftertaste/dependency-graph.json`。放在 current 之外：current 专门按源码路径镜像文件讲解，图则描述跨文件关系，且节点可能尚未生成讲解。闭环保存自己的参与内容，不把完整闭环资料塞入这个文件。此路径不替笔记、偏好、阅读方向或闭环目录作决定。
- 顶层保存格式标识 `format`、分析依据 `source_commit`、节点数组 `nodes` 和边数组 `edges`。源码提交由程序从确认的资料版本填写；它表达实际分析依据，更新时不能仅换提交号就声称图已适配新版本。重分析与更新收尾的具体接口随后衔接已有更新流程。
- 节点以源码项目相对路径 `path` 为标识，统一使用 `/`，不额外生成 UUID。路径沿用镜像命名的项目基准，所选项目与 Git 仓库根的映射仍需后续明确。建议另存 `analysis`，仅区分 `unreviewed`（已登记但未完成依赖核对）与 `reviewed`（AI 已核对该文件在当前分析范围内的依赖）；它不是讲解生成状态或用户理解状态，也不是依赖无遗漏的证明。图未登记的文件不能当成已分析。
- 边使用 `dependency`（被依赖文件）、`dependent`（使用者）、`reason`（简短依赖说明）；绘图方向为前者指向后者。相同文件对的多种依赖原因可合并为一条说明，先不引入关系类型枚举、边 UUID 或图数据库。
- 讲解是否存在从真实文档判断，不把生成／阅读／理解状态再复制到依赖图。阅读顺序仍由 AI 决定；节点分析状态只是避免把“尚未分析”显示成“无依赖”。
- 程序生成框架和固定版本字段，AI 提供文件关系、分析结论与说明；程序检查 JSON 结构、路径与节点引用、重复项等机械规则。语义是否正确仍由 AI 分析，格式通过不保证完整性。是否提供写入命令、具体参数及可检查范围，随后设计，不提前实现。

示例只说明候选数据形状，完整提交占位符不是可直接运行的数据；`schema.py`、`service.py` 也是假设文件：

```json
{
  "format": "aftertaste-dependency-graph/v1",
  "source_commit": "<完整 Git 提交 ID>",
  "nodes": [
    { "path": "backend/schema.py", "analysis": "reviewed" },
    { "path": "backend/service.py", "analysis": "reviewed" }
  ],
  "edges": [
    {
      "dependency": "backend/schema.py",
      "dependent": "backend/service.py",
      "reason": "service 使用 schema 定义的输入类型"
    }
  ]
}
```

单文件便于 AI 阅读、网页解析与程序检查，也便于重建；代价是图很大时修改会集中在同一文件。当前建议首版先不拆成每文件一份，也不用数据库；尚未做规模或性能实验，不承诺任意规模都适用。外部依赖、范围边界及更新时如何核对受影响节点，继续围绕该数据结构讨论，不在本轮擅自补成已确认规则。

### AI 建议：局部提交为常规路径，直接编辑为保底（未确认）

后续状态：U84 已确认局部查询、局部提交与程序合入、独立检查、直接编辑保底的维护方向。以下保留提出时状态，节点删除的关联处理与首次建图节奏见 U84 新建议。

建议最少提供三种能力，而不是大量逐节点命令：

1. 查询：按源码路径读取该文件已有依赖、使用者与分析状态，按需获取相关局部；不强制把整图塞进上下文。局部图不代替 AI 对固定源码的阅读。
2. 应用：AI 写一份小的 JSON 输入文件，程序按其中明确列出的文件合入主图。输入文件作为命令参数传入，避免在命令行里拼长 JSON。小文件是此次工具输入，不是第二份长期权威图；路径、命令名及清理方式尚未确定。
3. 检查：独立校验主图，供正常工具写入和 AI 直接编辑后共用；程序写入内部也使用相同检查规则。诊断给到 AI，指出文件／字段／关系及原因，不声称语义已正确。

推荐常规应用以“某个使用者文件当前依赖哪些文件”为单位提交完整结果。程序只替换 `dependent` 等于该文件的关系，保留其他使用者的关系。例：`service.py` 从依赖 `schema.py`、`old_repo.py` 改为依赖 `schema.py`、`new_repo.py`，输入新的两项，程序移除旧的 `old_repo.py → service.py` 并加入新关系；`service.py → router.py` 由 router 的依赖描述负责，本次不能一并抹去。同一文件的重复提交应得到同样结果，不累计重复边。

“完整结果”须由 AI 明确表示已核对完成；没分析完不能以空数组覆盖旧边。显式提交空依赖列表表示已核对且当前范围内未发现依赖；未提交的文件不改。局部发现只补一条边时不能冒充完整核对；可先读取已有局部并核实，或使用保底编辑，不在本轮擅自增加多套补丁接口。程序仍不能证明 AI 列表完整。

程序可检查输入及合并候选的格式、重复项、固定提交中的路径和节点引用；新引用的真实项目文件可登记为未分析节点，不能因被引用就标为已核对，也不据此扩大讲解范围。检查通过后先写临时文件再替换主图；失败返回诊断，保留原主图和输入供修复，不发布半份合并结果。这是写文件的局部可靠性建议，不增加复杂事务或自动恢复系统。结构检查通过仍不保证分析正确。

AI 直接编辑主 JSON 的保底入口已由作者要求保留；建议操作指南要求编辑后运行同一个检查工具。如果工具自身故障，明确报告未验证情况，允许 AI 查源码定位，不把“能直接编辑”表述为可以假称校验通过。主图已经损坏时，普通合并不应自动用空图替代，先输出诊断供修复。
