# 02 · 资料目录与文件映射

状态：讨论草稿。依据：[作者 U4、U6—U8、U14](../../../tasks/AR1-回甘首版需求设计/amendments.md)。返回[总入口](spec.md)。

## 已确认要求

- **FR-008**：生成的 Markdown 放在用户指定项目的 docs/aftertaste 下。（U4）
- **FR-009**：文件讲解根据用户指定项目的真实文件名命名。（U4）
- **FR-013**：从用户项目派生的讲解 Markdown、依赖图属于可重建资料；不能由用户项目重建的阅读器程序、渲染资源等必须保留。该分类不授予自动删除权。（U6）
- **FR-014**：用户手改讲解后展示修改后的内容，由用户承担其内容责任；不自动以重新生成的文本替代手改内容。后续主动更新的覆盖或合并策略仍待定。（U6）
- **LIMIT-001**：讲解内容依赖 AI，可能存在解释错误，这是项目接受的能力边界。脚本校验仅针对结构、源码定位及约定的覆盖范围；校验通过不代表解释正确，不据此追加未获批的语义审查系统。（U7）
- **FR-015**：文件讲解镜像源码目录，保留源码完整文件名后再加 .md；例如 backend/app/auth.py 对应 docs/aftertaste/backend/app/auth.py.md。（U8）
- **FR-016**：展示时发现文档不适配或阅读器专用解析失败，页面明确报错，提供让用户交给 AI 的修复提示词，同时按普通 Markdown 样式展示已有文档。不能依赖 AI 主动运行校验脚本才发现问题；由用户决定何时修复，不自动恢复或引入整套更新事务。（U8）

FR-008、009、015 规定产品运行后的讲解产物位置和命名。本项目用于开发讨论的 specs/ 不是这些产物，不混为同一目录。

## 用户场景与验收草案

用户指定项目并生成某份源码的讲解，能够在该项目 docs/aftertaste 下找到与真实源码名称对应的 Markdown。

命名验收至少包含：普通文件、不同目录同名文件、同一目录同主名但不同扩展名文件；按 FR-015 分别产生不同路径。降级验收：AI 留下不完整专用结构且未执行独立校验时，打开阅读页仍能看到错误、修复提示词和原文的普通 Markdown 展示，不把页面整体变成空白。

## 已确认的命名规则（U8）

镜像源码相对于目标项目的路径，并保留原扩展名后再加 .md。例如：

```text
源码：backend/app/auth.py
讲解：docs/aftertaste/backend/app/auth.py.md
```

保留原扩展名可区分 auth.py 与 auth.ts；镜像目录可区分 api/auth.py 与 services/auth.py。用户指定项目边界及重命名规则另行讨论。

## 定位建议（待确认）

不能仅凭文件名完成源码定位。建议资料级记录仓库、项目范围和提交；文件讲解记录源码相对路径；讲解段落记录源码行范围。字段承载方式尚未定，避免每篇独立维护可冲突的版本值。重命名时 Git 的相似度判断只能辅助匹配，不能保证恢复文档身份。

## 机器校验建议（U6 提议，规则待确认）

支持采用脚本校验，使结构错误可重复检查；但校验通过不能证明解释正确。

候选规则：

1. 必填元信息存在、格式正确，引用源码属于本套资料的选定提交。
2. 源码路径存在，行范围有效；若文档保存源码摘录，摘录须与指定范围一致。
3. U14 已确认文件讲解须完整展示该文件源码，每个对照块对应本文件的连续范围，见 [FR-024](06-document-blocks.md)。此前“可用略过记录代替完整展示、闭环文件讲解仅覆盖部分范围”的候选不再适用。是否允许范围重叠、如何排列等具体检查规则尚未确认。
4. 段落标识无冲突，引用目标存在，必需章节齐全；允许哪些 Markdown 格式由后续规范规定。

源码缺段可在覆盖约定明确后机器检查；AI 说错含义、遗漏业务解释不能只靠结构校验证明。U8 已确认展示时出错则提示并降级，不阻断普通 Markdown 阅读。专用结构解析与普通 Markdown 渲染应分开；若文件根本无法读取，不能声称已展示其原文。普通 Markdown 渲染器异常时是否再显示纯文本，是 AI 建议，尚未确定。

修复提示词建议包含：讲解文件路径、目标提交、对应源码路径、具体错误和相关片段；不依赖用户自行拼接。这些字段及提示文案待定。版本对应错误也须有可检查依据，不能承诺仅靠语法解析发现所有中断状态。

## 重建与手改的边界

项目派生资料可以重新生成，但 AI 重生成不保证逐字相同；用户手写补充也未必能从源码恢复。按 U6，目前接受手改内容由用户负责，不自行扩展自动备份或编辑历史功能。允许工具在用户主动更新时怎样处理这些补充，仍需单独确认。

验收草案：合法的手改讲解经过选定刷新流程后展示修改结果；重建派生资料不会覆盖阅读器程序。校验失败按 FR-016 处理；刷新流程尚未确定。

## 需要讨论的底层选择

| 议题 | 未决问题 |
| --- | --- |
| 路径基准 | 镜像相对于用户指定子目录，还是整个 Git 仓库根 |
| 文档身份 | 文件重命名或移动后，旧讲解如何定位、保留和继续维护 |
| 内容边界 | 哪些属于讲解正文，哪些是源码版本、范围、定位等元信息 |
| 元信息承载 | 信息放在 Markdown 内，还是单独索引；哪一份是权威来源 |
| 多文件内容 | 闭环总览和跨文件说明放在哪里，如何避免与源码镜像命名冲突 |
| 原始与生成资料 | 可重建原则已确认；索引、快照、缓存和个人记录的具体归属与重建流程待定 |
| 个人内容 | 进度、疑问、批注是否随项目保存，是否与讲解文档分开 |
| 定位 | 行号之外是否还需要原文或段落标识，防止代码插行、文档改写后错位 |
| 写入边界 | 哪些目录允许工具写入；用户修改的讲解如何在更新时保全 |
| 失败与恢复 | 已确认错误提示、修复提示词与普通 Markdown 降级；具体检测规则和提示词内容待定 |

## 关键实体与成功标准

已涉及源码文件、文件讲解和目标项目三个概念；其完整身份规则尚未确定。

FR-008 可核对输出目录，FR-009、015 的普通文件命名已明确；目录冲突及重命名策略仍需补充。
